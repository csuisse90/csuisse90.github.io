    a: >-

  - q: >-

    a: >-
      An attribute, or combination of attributes, that uniquely identifies each row. It cannot be duplicated and cannot be empty.
  - q: >-

    a: >-
      An attribute in one table that refers to the primary key of another, which is how a relationship between the two is recorded.
  - q: >-

    a: >-
      A primary key made of more than one attribute, used when no single attribute is unique on its own.
  - q: >-

    a: >-
      The rule that every primary key value must be present and unique, so every row can be told apart from every other.
  - q: >-

    a: >-
      The rule that a foreign key must either be empty or match an existing primary key, so nothing refers to a row that is not there.
  - q: >-

Put everything in one big table and it works, briefly, for small amounts of data.
The trouble starts on the first update.

## Why one table fails

Consider a library keeping loans in a single table:

| LoanID | MemberName | MemberAddress | BookTitle | Author | DateOut |
| --- | --- | --- | --- | --- | --- |
| 1 | A. Lovelace | 12 Mill St | Gödel, Escher, Bach | Hofstadter | 2026-03-01 |
| 2 | A. Lovelace | 12 Mill St | The Mythical Man-Month | Brooks | 2026-03-04 |
| 3 | G. Hopper | 9 Bank Rd | Gödel, Escher, Bach | Hofstadter | 2026-03-06 |

Three problems, each with a name.

**Update anomaly.** Lovelace moves house. Her address appears in two rows here and
possibly two hundred in a real system. Miss one and the database now holds two
different addresses for the same person, with nothing to say which is right.

**Insertion anomaly.** A new member joins but has borrowed nothing. There is
nowhere to record them, because a row of this table requires a loan.

**Deletion anomaly.** The last loan of a book is deleted, and with it the only
record that the library owns that book, and who wrote it.

All three come from the same cause: **facts about different things are stored
together**. The fix is to store facts about members in a Member table, facts about
books in a Book table, and facts about loans in a Loan table.

## Keys

A **primary key** uniquely identifies a row. It must be unique and must never be
empty — that rule is **entity integrity**, and without it you have rows you cannot
tell apart or refer to.

Sometimes no single attribute is unique, and a **composite key** of two or more
attributes is used. In a table of exam entries, neither StudentID nor SubjectCode
is unique alone, but the pair identifies exactly one entry.

A **foreign key** is an attribute holding a primary key value from another table.
`Loan.MemberID` holding `M104` says this loan belongs to that member. This is the
entire mechanism by which relational databases represent relationships — there are
no pointers, no nesting, just matching values.

**Referential integrity** is the rule that a foreign key must match an existing
primary key, or be null. It is what stops a loan referring to a member who has been
deleted.

<Aside kind="why" title="Why a natural key is usually a bad primary key">
It is tempting to use something already unique — an email address, a national
insurance number, an ISBN.

It goes wrong for reasons that are obvious in hindsight. People change email
addresses, and the change now has to propagate to every foreign key referring to
it. Values thought to be unique turn out not to be: ISBNs have been reissued, and
two people have shared a national insurance number through administrative error.
And a real-world identifier is often sensitive, so it ends up copied into a dozen
tables that had no business holding it.

A **surrogate key** — an arbitrary integer with no meaning outside the database —
avoids all of this. It never changes, because nothing in the real world can change
it. Almost every production database uses one.
</Aside>

## Relationships

**One-to-one.** Each row in A relates to at most one in B. Genuinely rare, and
usually a sign the two tables should be merged. It is defensible when part of the
data is sensitive or rarely used and worth separating.

**One-to-many.** The common case. One member has many loans; each loan belongs to
one member. Implemented by putting a foreign key on the **many** side — `MemberID`
goes in Loan, not the other way round.

**Many-to-many.** Each member borrows many books; each book is borrowed by many
members. This **cannot** be implemented directly. There is no way to put a foreign
key on either side without repeating rows.

The solution is a **link table** holding a foreign key to each side. Loan is
exactly that, and note what it enables: because the relationship now has a table of
its own, it can carry attributes — the date borrowed, the date due, whether it was
renewed. Those facts belong to the *relationship*, not to the member or the book.

<Aside kind="trap" title="Putting the foreign key on the wrong side">
For a one-to-many relationship, the foreign key goes on the **many** side. Always.

Put `LoanID` in Member instead and a member can have exactly one loan, because
there is one column to hold it. Trying to fix that with `Loan1`, `Loan2`, `Loan3`
columns is the classic wrong answer: it caps the number arbitrarily, wastes space
on members who have borrowed nothing, and makes "find all loans" impossible to
write as a query.

The test to apply: which side can there be many of? That side gets the foreign key.
</Aside>

<Py caption="The three anomalies, demonstrated. Run it to see the one-table design go inconsistent, then the normalised version refuse to.">{`
# One table: the same fact in several places.
flat = [
    {"loan": 1, "member": "A. Lovelace", "address": "12 Mill St", "book": "GEB"},
    {"loan": 2, "member": "A. Lovelace", "address": "12 Mill St", "book": "MMM"},
    {"loan": 3, "member": "G. Hopper",   "address": "9 Bank Rd",  "book": "GEB"},
]

print("Lovelace moves house, and one row is missed:")
for row in flat:
    if row["member"] == "A. Lovelace" and row["loan"] == 1:
        row["address"] = "44 Quay St"

addresses = {r["address"] for r in flat if r["member"] == "A. Lovelace"}
print("   addresses now on record for her:", addresses)
print("   consistent:", len(addresses) == 1)

# Split into tables: the address exists once, so it cannot disagree with itself.
members = {"M1": {"name": "A. Lovelace", "address": "12 Mill St"},
           "M2": {"name": "G. Hopper",   "address": "9 Bank Rd"}}
books   = {"B1": {"title": "GEB"}, "B2": {"title": "MMM"}}
loans   = [{"id": 1, "member": "M1", "book": "B1"},
           {"id": 2, "member": "M1", "book": "B2"},
           {"id": 3, "member": "M2", "book": "B1"}]

members["M1"]["address"] = "44 Quay St"
print()
print("after the same move, normalised:")
for loan in loans:
    m = members[loan["member"]]
    print(f"   loan {loan['id']}: {m['name']:<12} {m['address']:<12} {books[loan['book']]['title']}")

# Referential integrity: a loan may not point at a member who is not there.
def add_loan(loan):
    if loan["member"] not in members:
        raise ValueError(f"referential integrity: no member {loan['member']}")
    loans.append(loan)

print()
try:
    add_loan({"id": 4, "member": "M9", "book": "B1"})
except ValueError as e:
    print("  ", e)
`}</Py>

<Takeaway>
Store each fact in exactly one place, and connect the places with keys. Every rule
in the relational model — entity integrity, referential integrity, normalisation —
exists to enforce that one sentence.
</Takeaway>
