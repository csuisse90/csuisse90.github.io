A single SQL statement either works or it does not. Real operations are rarely a
single statement.

Transferring money is two: subtract from one account, add to another. If the
machine fails between them, the money has vanished. No amount of care in writing
each statement prevents that, because the problem is the gap between them.

## Transactions

A **transaction** groups operations so they count as one indivisible action.

```sql
BEGIN TRANSACTION;
  UPDATE Account SET balance = balance - 500 WHERE id = 'A';
  UPDATE Account SET balance = balance + 500 WHERE id = 'B';
COMMIT;
```

Either both updates take effect, or — if anything fails before the `COMMIT` — the
system performs a **rollback** and neither does. There is no state in which the
money is in flight.

## ACID

**Atomicity** — all or nothing. The transaction is a single point of failure by
design, so there is never a half-applied change.

**Consistency** — every transaction takes the database from one valid state to
another. Integrity rules such as referential integrity hold before and after; they
may be momentarily suspended inside, but never at a point anyone can observe.

**Isolation** — concurrent transactions behave as though they had run one after
another. Nobody sees anybody else's unfinished work.

**Durability** — once committed, it survives. The change is on non-volatile storage
before the commit is acknowledged, so a power cut a millisecond later loses
nothing.

<Aside kind="deeper" title="How durability is actually achieved without waiting for the disc">
Writing every change to its final place on disc before confirming a commit would be
unbearably slow, because those places are scattered.

Real systems use **write-ahead logging**. Before touching the data, the intended
change is appended to a log file — a single sequential write, which is the fastest
thing a disc does. Only once the log entry is safely stored is the commit
confirmed. The actual data pages are updated later, at leisure.

If the machine crashes, the log is replayed on restart: committed transactions
found in the log are reapplied, uncommitted ones are undone. The database recovers
to a consistent state without having waited for anything during normal operation.

This is the same idea as a journalling file system, and for the same reason.
</Aside>

## What isolation protects you from

Without it, two specific things go wrong.

**Lost update.** Two transactions read a stock level of 10. Each subtracts one and
writes 9. Two items were sold; the database says one was.

**Dirty read.** One transaction reads a value another has written but not yet
committed. If the second transaction is rolled back, the first has acted on data
that never officially existed.

The usual mechanism is **locking**: a transaction takes a lock on a row before
changing it, and others wait. Which creates its own problem.

**Deadlock.** Transaction 1 locks row A and wants row B. Transaction 2 locks row B
and wants row A. Both wait forever. The system detects the cycle — usually by
looking for a loop in a wait-for graph, or simply by timeout — and aborts one,
rolling it back so the other can proceed.

<Py caption="The lost update, then the same operation done safely. Step through the unsafe version and watch both transactions read the same starting value.">{`
class Row:
    def __init__(self, value):
        self.value = value
        self.locked_by = None

stock = Row(10)

# Unsafe: both read before either writes.
read_by_1 = stock.value
read_by_2 = stock.value
stock.value = read_by_1 - 1     # transaction 1 sells one
stock.value = read_by_2 - 1     # transaction 2 sells one, overwriting
print("without locking")
print(f"   both read {read_by_1}, both wrote {stock.value}")
print(f"   two items sold, stock fell by {10 - stock.value} — one update lost")

# Safe: a lock forces the second transaction to read after the first has written.
stock = Row(10)
log = []

def sell(name):
    if stock.locked_by is not None:
        log.append(f"{name} waits for {stock.locked_by}")
        return False
    stock.locked_by = name
    current = stock.value
    stock.value = current - 1
    log.append(f"{name} read {current}, wrote {stock.value}")
    stock.locked_by = None
    return True

print()
print("with locking")
sell("T1")
sell("T2")
for line in log:
    print("  ", line)
print(f"   stock fell by {10 - stock.value} — both updates kept")

print()
a, b = Row(1), Row(2)
a.locked_by, b.locked_by = "T1", "T2"

print(f"   T2 holds B and wants A (held by {a.locked_by})")
print("   neither can proceed; the system must abort one and roll it back")

## When relational is the wrong model

The relational model assumes data has a regular shape known in advance. Sometimes
it does not.

**Document databases** store self-contained records — typically JSON — that need
not share a structure. A book has an author, a shirt has a size, and neither wastes
a column on the other's attributes. Good when records vary, when the schema changes
frequently, and when data is read whole rather than joined.

**Key-value stores** are a dictionary at scale: give a key, get a value. Extremely
fast, extremely limited, ideal for caches and sessions.

**Graph databases** store nodes and the edges between them, and make "friends of
friends of friends" cheap — a query that requires an unbounded chain of joins in
SQL.

**Data warehouses** are relational but deliberately denormalised, holding historical
data gathered from several systems for analysis. They are optimised for reading
enormous quantities, not for updating.

<Aside kind="trap" title="NoSQL does not mean "no rules", it means the rules move">
The attractive framing is that NoSQL databases are simpler because they drop
schemas and joins. What actually happens is that the work moves into the
application.

Without a schema, nothing stops two records disagreeing about whether the field is
called `postcode` or `postCode`, and the code must cope with both. Without foreign
keys, nothing stops an order referring to a deleted customer. Without transactions
across records, keeping two documents in step becomes your problem.

A defensible answer says what is gained (scale, flexibility, speed of change) and
where the cost lands (integrity becomes the application's responsibility), rather
than treating one model as modern and the other as obsolete.
</Aside>

<Takeaway>
ACID exists because the interesting failures happen *between* statements, not
inside them. NoSQL relaxes those guarantees to buy scale, and whether that is a
bargain depends entirely on what a wrong answer costs you.
</Takeaway>
