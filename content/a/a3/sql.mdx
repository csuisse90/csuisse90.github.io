  - q: >-

    a: >-
      `COUNT`, `SUM`, `AVG`, `MIN` and `MAX` — each collapses many rows into one value.
  - q: >-

    a: >-
      Splits rows into groups sharing a value, so an aggregate is computed per group rather than over the whole table.
  - q: >-
      What is the difference between WHERE and HAVING?
    a: >-
      `WHERE` filters rows **before** grouping; `HAVING` filters groups **after** aggregation. You cannot use an aggregate in `WHERE`.
  - q: >-

    a: >-
      Removes duplicate rows from the result.
  - q: >-
      Which statements modify data rather than read it?

  - q: >-

    a: >-

SQL is **declarative**, and that is its defining feature. You describe the result
you want; the database decides how to obtain it — which index to use, which table
to scan first, whether to sort now or later. Two queries that ask for the same
thing in different words may run identically, because the optimiser rewrites both
into the same plan.

## The shape of a query

```sql
SELECT   name, year
FROM     Student
WHERE    year = 12
ORDER BY name ASC;
```

- **SELECT** — which columns.
- **FROM** — which table.
- **WHERE** — which rows.
- **ORDER BY** — in what order.

That covers a surprising proportion of everything ever asked of a database.

<Aside kind="why" title="The clauses do not run in the order they are written">
SQL is written `SELECT … FROM … WHERE …` but evaluated roughly
`FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY`.

This is not trivia. It explains two things that otherwise look arbitrary.

First, why you cannot use a column alias defined in `SELECT` inside `WHERE`: the
alias does not exist yet when `WHERE` runs.

Second, why an aggregate cannot appear in `WHERE`. `COUNT(*)` is produced by
`GROUP BY`, which has not happened when `WHERE` is filtering rows. That is exactly
why `HAVING` exists — it is the filter that runs *after*.
</Aside>

## Joins

Normalisation split the data up; joins put it back together for one query.

```sql
SELECT   Member.name, Book.title, Loan.dateOut
FROM     Loan
JOIN     Member ON Loan.memberID = Member.memberID
JOIN     Book   ON Loan.bookID   = Book.bookID;
```

Each `ON` clause matches a foreign key against the primary key it refers to.

An **inner join** — the default — returns only rows that match on both sides. A
member who has borrowed nothing does not appear at all.

A **left join** returns every row from the left table, filling the right-hand
columns with nulls where there is no match. This is how you find absences:

```sql
SELECT   Book.title
FROM     Book
LEFT JOIN Loan ON Book.bookID = Loan.bookID
WHERE    Loan.loanID IS NULL;
```

Every book that has never been borrowed. An inner join cannot express this,
because the rows you want are precisely the ones it discards.

## Aggregates and grouping

Aggregate functions collapse many rows into one value: `COUNT`, `SUM`, `AVG`,
`MIN`, `MAX`.

```sql
SELECT   Member.name, COUNT(*) AS loans
FROM     Member
JOIN     Loan ON Member.memberID = Loan.memberID
GROUP BY Member.memberID, Member.name
HAVING   COUNT(*) > 3
ORDER BY loans DESC;
```

`GROUP BY` splits the rows into one group per member; `COUNT(*)` counts within each
group; `HAVING` throws away the small groups afterwards.

## Changing data

```sql
INSERT INTO Member (memberID, name) VALUES ('M4', 'K. Iverson');
UPDATE Member SET name = 'A. King' WHERE memberID = 'M1';
DELETE FROM Loan WHERE dateOut < '2026-01-01';
```

The `WHERE` clause on `UPDATE` and `DELETE` is not optional in practice. Omit it
and the statement applies to **every row in the table**, silently and
irreversibly.

## SQL injection

Building a query by pasting user input into a string is the most consequential
mistake in this topic.

```python
# Never do this.
query = "SELECT * FROM User WHERE name = '" + name + "' AND pass = '" + password + "'"
```

Enter `' OR '1'='1` as the password and the query becomes:

```sql
SELECT * FROM User WHERE name = 'admin' AND pass = '' OR '1'='1'
```

`'1'='1'` is always true, so the query returns every user and the login succeeds
without a password. Worse inputs can read other tables or destroy them.

The fix is a **parameterised query**, where the SQL and the values travel
separately and the database never parses input as SQL:

```python
db.execute("SELECT * FROM User WHERE name = ? AND pass = ?", (name, password))
```

<Aside kind="trap" title="Escaping quotes is not the fix, and examiners know it">
A common wrong answer is "check the input for apostrophes" or "remove dangerous
characters".

This fails because the list of dangerous input is longer than anyone's imagination,
and because different databases and character encodings offer different ways to
smuggle a quote through. Every blocklist ever written has eventually been got past.

Parameterisation works for a structurally different reason: the query is parsed
*before* the values are supplied, so there is no moment at which the input could
be read as syntax. The mark is for saying that, not for saying "sanitise the
input".
</Aside>

<Takeaway>
`WHERE` filters rows, `HAVING` filters groups, joins reassemble what
normalisation separated, and user input never becomes part of the query text.
</Takeaway>
