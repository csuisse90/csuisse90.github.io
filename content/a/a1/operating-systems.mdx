      Name the main functions of an operating system.

    a: >-

    a: >-
      Running several processes on one processor by switching between them so quickly that all appear to progress at once.
  - q: >-

    a: >-
      Saving one process's registers and state, then loading another's, so execution can resume exactly where it left off. It is pure overhead — no useful work happens during it.

      What is a device driver?
    a: >-
      Software that translates the operating system's general requests into the specific commands a particular piece of hardware understands.
  - q: >-
      Why is a driver needed at all?
    a: >-
      Every device is different. Without drivers, every application would need code for every model of printer, disc and graphics card in existence.
  - q: >-
      What is the kernel?
    a: >-
      The core of the operating system, always in memory, running with full hardware privileges and handling the most fundamental services.
  - q: >-

      What is a system call?
    a: >-
      A controlled request from a user-mode program asking the kernel to do something privileged on its behalf, such as reading a file.

Without an operating system, every program would need its own code for the exact
disc controller fitted, its own way of putting pixels on the exact screen
attached, and a private agreement with every other program about who may use the
memory. Nothing would be portable and nothing would be safe.

The operating system exists so that no application has to know any of that.

## Program, process, thread

A **program** is a file on disc: passive, just instructions.

A **process** is that program running. It has memory allocated to it, a set of
register values, a program counter saying where it has got to, and a list of open
files. Two copies of the same editor are one program and two processes, each with
its own state.

A **thread** is a strand of execution within a process. Threads of the same process
share its memory, which makes communication between them cheap and makes it very
easy for them to corrupt each other's data.

## Managing the processor

One processor core runs one instruction stream. Yet dozens of processes appear to
run at once.

They do not. The operating system switches between them fast enough that a human
cannot tell — tens or hundreds of times a second. This is **multitasking**, and
the switch itself is a **context switch**:

1. A timer interrupt fires, transferring control to the kernel.
2. The running process's registers, program counter and flags are saved into its
   process control block.
3. The scheduler chooses which process runs next.
4. That process's saved state is loaded back into the registers.
5. Execution resumes, and the process is none the wiser.

A context switch does no useful work. It is overhead, paid for the illusion of
simultaneity, which is why switching too often makes a system slower rather than
more responsive.

<Aside kind="why" title="Why the timer interrupt is what makes this possible at all">
There is a bootstrapping problem here worth noticing. If a process is running, the
operating system is not. So how does the operating system ever get control back
from a program that does not cooperate?

The answer is hardware. A timer chip counts down and raises an **interrupt** on the
control bus, which forces the processor to stop, save its state and jump to a fixed
address where the kernel's handler lives. The running program has no say in it.

Early systems lacked this and used **cooperative** multitasking, where each program
was trusted to hand control back voluntarily. One program with an infinite loop
froze the entire machine, which is exactly what happened routinely on machines of
that era. Pre-emption is not an optimisation; it is what makes an operating system
able to enforce anything at all.
</Aside>

## Managing memory

Several processes are in memory at once, and none may read or write another's.

The operating system allocates each process a region and, with help from hardware,
enforces the boundary. An attempt to read outside it is caught by the memory
management unit, which raises an exception rather than allowing the access — the
segmentation fault familiar to anyone who has written C.

Processes also see **virtual addresses**, translated to physical ones by the
hardware. Two processes can both use address $0$ without conflict, because those
map to different physical locations. This is also what allows virtual memory to
move a page out to disc and back to a different physical address, invisibly.

## Managing files

Storage is physically a numbered sequence of blocks. Nobody wants to work in those
terms, so the file system presents named files in a hierarchy of directories and
keeps track of which blocks hold which file.

It also handles permissions, free space, and — crucially — the metadata that makes
recovery possible after a crash, which is what journalling file systems add.

## Kernel mode and user mode

The processor itself supports two privilege levels, and this hardware feature is
what makes an operating system enforceable.

In **kernel mode**, all instructions are permitted and all memory is reachable.
The kernel runs here.

In **user mode**, privileged instructions — those that touch hardware, alter the
memory map, or disable interrupts — simply fail. Applications run here.

So how does a program read a file, if it cannot touch the disc? It makes a
**system call**: a deliberate, controlled transition into kernel mode at a fixed
entry point, with the kernel deciding whether to comply.

<Aside kind="deeper" title="The system call is the whole security model">
Every restriction an operating system enforces rests on this one mechanism. A
program cannot read another process's memory, cannot write to a file it lacks
permission for, and cannot reprogram the network card, because all three require
instructions it is not allowed to execute.

The only way through is a system call, and a system call is a request the kernel
may refuse. Notice the shape of the argument: security comes from the fact that
the check happens on the *other* side of a boundary the untrusted code cannot
cross.

This is also why a bug in the kernel is so much more serious than a bug in an
application. The application is inside the fence; the kernel is the fence.
</Aside>

<Takeaway>
An operating system is a manager of scarce resources — processor time, memory,
storage, devices — and an enforcer of boundaries between the programs competing
for them. Both jobs depend on hardware support: the timer interrupt and the
privilege levels.
</Takeaway>
