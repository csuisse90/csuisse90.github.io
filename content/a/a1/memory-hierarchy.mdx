      Registers (fastest, smallest, dearest), then cache, then RAM, then secondary storage (slowest, largest, cheapest). Speed, cost per bit and capacity all trade against each other.

  - q: >-

    a: >-
      The observation that programs tend to reuse the same data soon (**temporal**) and to use data stored nearby (**spatial**). Caching only works because this is true.

Ask why a computer does not simply have one large, fast memory and the honest
answer is that nobody knows how to make one at a price anybody would pay. Every
memory technology trades speed against cost per bit, and no technology wins on
both. So machines are built out of several kinds at once, arranged so the fast
expensive stuff sits in front of the slow cheap stuff.

## Primary memory: what the CPU can reach

**Primary memory** means memory the processor can address directly — put an
address on the address bus and the contents come back. That is RAM and ROM.
Everything else, however fast, is secondary: the CPU cannot read a hard disc by
naming an address, it has to ask the operating system to fetch it.

**RAM** is where running programs and their data live. It is read/write and it is
**volatile**: cut the power and it is gone. The name is a historical accident —
"random access" meant any location costs the same to reach, as opposed to tape,
where reaching the middle means winding through everything before it. Every
memory in a modern computer is random access in that sense, so the name no longer
distinguishes anything.

**ROM** holds the instructions the machine needs before it has loaded anything.
This is the answer to a question worth taking seriously: at the instant you press
the power button, RAM contains noise, there is no operating system, and the
program counter is about to be set to some fixed address. Whatever is at that
address had better be a real instruction. So it is in ROM, it is called the
**bootstrap**, and its job is to find and load enough of the operating system to
load the rest.

<Aside kind="history" title="Why it is called bootstrapping">
From "to pull oneself up by one's own bootstraps" — a deliberately absurd image,
because the machine appears to start itself from nothing. The joke stuck, and
gave us the verb "to boot". The absurdity is resolved by the ROM: the machine
does not start from nothing, it starts from a small program somebody put in
hardware in advance.
</Aside>

## The hierarchy, level by level

| Level | Typical size | Typical access time | Cost per bit |
| --- | --- | --- | --- |
| Registers | a few hundred bytes | $0.3\,\text{ns}$ | highest |
| L1 cache | 32–64 KiB | $1\,\text{ns}$ | very high |
| L2 / L3 cache | 256 KiB – 32 MiB | $4$–$20\,\text{ns}$ | high |
| Main memory (RAM) | 8–64 GiB | $60\,\text{ns}$ | moderate |
| SSD | 0.5–4 TiB | $50{,}000\,\text{ns}$ | low |
| Hard disc | 1–20 TiB | $5{,}000{,}000\,\text{ns}$ | lowest |

Those numbers deserve a moment, because the ratios are hard to feel. If a
register access took one second, then main memory would take about three minutes,
an SSD would take a day and a half, and a hard disc seek would take five months.
This is why a processor waiting on memory is such a catastrophe, and why so much
of computer architecture is arrangements for not waiting.

## Cache, and why it works at all

**Cache** is a small amount of SRAM sitting between the CPU and main memory. When
the CPU asks for an address, the cache is checked first. Found — a **hit** — and
the value arrives in a nanosecond or two. Not found — a **miss** — and the full
memory access happens, with the value copied into cache on the way past in case it
is wanted again.

The part that should bother you is why this ever helps. Cache is thousands of
times smaller than main memory. If a program touched addresses at random, the
chance of a hit would be vanishingly small and cache would be pointless.

Programs do not touch addresses at random. They exhibit **locality of reference**,
in two flavours:

- **Temporal locality** — data used once is likely to be used again soon. A loop
  counter is read and written on every iteration.
- **Spatial locality** — data near recently used data is likely to be used next.
  Walking through an array touches consecutive addresses.

Cache exploits both: a hit satisfies temporal locality, and because a miss fetches
a whole **cache line** — typically 64 bytes, not the single byte requested — the
neighbours come along too, satisfying spatial locality in advance.

<Aside kind="deeper" title="A hit rate of 90% is not 90% of the benefit">
Take the numbers from the practice question: a 2 ns cache and a 60 ns memory, with
90% hits. Average access is $0.9(2) + 0.1(60) = 7.8\,\text{ns}$.

Now notice how that time is spent. The 90% of accesses that hit contribute
$1.8\,\text{ns}$; the 10% that miss contribute $6.0\,\text{ns}$. **More than three
quarters of the total time is spent on one access in ten.** Raise the hit rate to
99% and average access falls to $2.6\,\text{ns}$ — a further threefold improvement
from a change that sounds like a rounding error.

This is why cache design is obsessive about the last few per cent, and it is a good
general lesson: when one branch of an average is much larger than the other, the
average is governed by the rare expensive case, not the common cheap one.
</Aside>

<Py caption="The arithmetic above, made adjustable. Change the hit rate and watch how sharply average access time falls near the top of the range.">{`
CACHE_NS = 2
MEMORY_NS = 60

print(f"{'hit rate':>9} {'average':>9}  {'':<24}")
for percent in (0, 50, 80, 90, 95, 99, 99.9):
    h = percent / 100
    average = h * CACHE_NS + (1 - h) * MEMORY_NS
    bar = "#" * round(average / 2)
    print(f"{percent:>8}% {average:>8.2f}ns  {bar}")
`}</Py>

## Virtual memory

Suppose a program needs more memory than the machine has. Rather than refusing to
run it, the operating system pretends there is more, keeping the parts not
currently in use out on the disc and fetching them back when they are touched.
That is **virtual memory**, and the units moved back and forth are **pages**.

It works, and it is why you can open a very large file on a modest machine. What
it costs is speed: a page fetched from disc is, on the numbers above, tens of
thousands of times slower than one already in RAM. When demand rises far enough
that the system spends most of its time shuffling pages rather than running code,
it is **thrashing**, and the symptom is a machine that becomes unusably slow while
the disc light stays on.

<Takeaway>
Every level of the hierarchy is the same bargain: keep the small amount you are
using now somewhere fast, and everything else somewhere cheap. Cache does it
between CPU and RAM. Virtual memory does it between RAM and disc.
</Takeaway>
