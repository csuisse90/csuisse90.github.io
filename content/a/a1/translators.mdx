A processor executes machine code and nothing else. Anything written in a language
a person would willingly use has to be translated first, and there are two quite
different ways to arrange that.

## The layers

| Level | Example | Who reads it |
| --- | --- | --- |
| High-level language | `total = price * quantity` | People |
| Assembly language | `LDA price` / `MUL quantity` / `STA total` | People, just about |
| Machine code | `0001 0000 0110 0100` | The processor |

**Assembly language** is machine code with the bit patterns replaced by mnemonics.
The correspondence is essentially one instruction to one line, so an **assembler**
does very little: look up each mnemonic, work out what address each label refers
to, emit the bytes.

High-level languages are a much bigger jump. One line of Python may become dozens
of machine instructions, and the translator has real work to do.

## Compilers and interpreters

A **compiler** translates the whole program once, in advance, producing an
executable file. Translation and execution are separate events, possibly years
apart.

An **interpreter** translates and executes as it goes, statement by statement,
every time the program runs. No executable is produced.

<Compare />

The consequences follow from that one difference:

**Speed of running.** Compiled code wins, and not marginally. An interpreter
re-analyses a statement every time it is reached — inside a loop running a million
times, that is a million redundant analyses.

**Speed of starting.** Interpreted code wins. There is no wait before the first
line runs, which matters enormously when you are changing the code every thirty
seconds.

**Error reporting.** A compiler finds every syntax error before anything runs,
which is thorough but means fixing a hundred errors before seeing any behaviour.
An interpreter reports the first error when it reaches it — so a mistake on the
last line of a long program is not discovered until the program has run all the way
there.

**Portability.** Machine code is specific to one processor family, so a compiled
program must be rebuilt for each target. Source code plus an interpreter runs
anywhere the interpreter has been ported.

**Secrecy.** Distributing an executable does not hand over the source. Distributing
a Python script does.

<Aside kind="trap" title="Neither is “better” — and questions are testing whether you know that">
Answers that say "compilers are better because they are faster" lose marks, and so
do answers that say "interpreters are better because they are easier to debug".
Both are one-sided.

The examinable skill is matching the property to the scenario. Look for what the
question emphasises: distribution to customers, execution speed, or protecting
source code all point at a compiler. Rapid development, cross-platform use, or
teaching beginners all point at an interpreter.
</Aside>

## Inside a compiler

**Lexical analysis** breaks the character stream into **tokens**. `total = price *
2` becomes identifier, assignment, identifier, operator, literal. Whitespace and
comments are discarded, and identifiers are recorded in a **symbol table**. An
error here means a character sequence that is not a valid token at all.

**Syntax analysis** checks the token sequence against the grammar and builds a
**parse tree**. A missing bracket or a misplaced keyword is caught here — these are
**syntax errors**.

**Semantic analysis** asks whether the grammatically valid program actually means
anything. Is that variable declared? Do the types match? Is a function being called
with the right number of arguments? A program can be perfectly grammatical and
still meaningless, in exactly the way "the number seven ate Tuesday" is.

**Code generation** produces machine code, or an intermediate form.

**Optimisation** improves it: removing calculations whose results are never used,
computing constant expressions at compile time, moving invariant work out of loops,
keeping hot variables in registers.

<Py caption="A compiler's first two stages, on real input. Step through and watch the token list grow, then the tree assemble from it.">{`
import re

TOKENS = [
    ("NUMBER",  r"\\d+(\\.\\d+)?"),
    ("NAME",    r"[A-Za-z_]\\w*"),
    ("OP",      r"[+\\-*/=()]"),
    ("SKIP",    r"[ \\t]+"),
]
MASTER = "|".join(f"(?P<{name}>{pattern})" for name, pattern in TOKENS)

def lex(source):
    out = []
    for match in re.finditer(MASTER, source):
        kind = match.lastgroup
        if kind != "SKIP":
            out.append((kind, match.group()))
    return out

source = "total = price * quantity + 20"
tokens = lex(source)
print("source:", source)
print("tokens:")
for kind, text in tokens:
    print(f"    {kind:<7} {text}")

# Syntax analysis: a tiny precedence-climbing parser for arithmetic.
def parse(tokens):
    pos = 0
    def peek():
        return tokens[pos][1] if pos < len(tokens) else None
    def take():
        nonlocal pos
        pos += 1
        return tokens[pos - 1][1]
    def atom():
        if peek() == "(":
            take()
            inner = expression(0)
            take()
            return inner
        return take()
    def expression(min_power):
        left = atom()
        while peek() in ("+", "-", "*", "/"):
            op = peek()
            power = 2 if op in "*/" else 1
            if power < min_power:
                break
            take()
            right = expression(power + 1)
            left = (op, left, right)
        return left
    return expression(0)

tree = parse([t for t in tokens if t[1] != "="][1:])
print()
print("parse tree for the right-hand side:")

def show(node, depth=0):
    pad = "    " * depth
    if isinstance(node, tuple):
        print(f"{pad}{node[0]}")
        show(node[1], depth + 1)
        show(node[2], depth + 1)
    else:
        print(f"{pad}{node}")

show(tree)
print()
print("note that * binds tighter than +, so it sits deeper in the tree")
`}</Py>

## Bytecode, and the middle way

Java and Python do neither of the above exactly. They **compile to bytecode** — a
compact instruction set for a machine that does not physically exist — and then a
**virtual machine** interprets that.

This buys most of both bargains. The expensive analysis happens once, at compile
time, so it is far faster than interpreting source text. The bytecode is
machine-independent, so it runs anywhere the virtual machine has been ported.

<Aside kind="deeper" title="Just-in-time compilation, or how an interpreted language got fast">
A virtual machine can watch its own execution. If a method has been called ten
thousand times, it is worth spending real effort compiling *that* method to native
machine code and using the compiled version thereafter. This is **JIT
compilation**.

The surprising part is that a JIT can sometimes beat an ahead-of-time compiler. It
knows things a static compiler cannot: which branch is actually taken, which types
actually turn up at a call site, what the input data actually looks like. It can
compile a specialised version on that basis and fall back if the assumption stops
holding.

This is why "interpreted languages are slow" is now a considerable
over-simplification, and why the compiler-versus-interpreter distinction is best
understood as two ends of a spectrum that real systems sit between.
</Aside>

<Takeaway>
A compiler pays the translation cost once and hands you a machine-specific
artefact. An interpreter pays it every time and hands you portability and a fast
edit-run loop. Bytecode splits the difference, which is why most modern languages
use it.
</Takeaway>
