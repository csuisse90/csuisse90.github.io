A computer stores numbers. It has no notion of a letter. So text is stored by
agreeing, in advance and universally, which number stands for which character —
and then storing numbers.

The agreement is the hard part, and the history of getting it wrong is more
instructive than the final answer.

## ASCII

The **American Standard Code for Information Interchange**, settled in 1963, uses
seven bits and therefore defines $2^7 = 128$ characters. Codes $0$–$31$ are
**control characters**, which are instructions rather than marks: newline, tab,
carriage return, and a set of teleprinter commands now mostly forgotten. Codes
$32$–$126$ are the printable ones, and $127$ is delete.

| Range | Contents |
| --- | --- |
| 0–31 | Control codes (newline is 10, tab is 9) |
| 32–47 | Space and punctuation |
| 48–57 | Digits `0`–`9` |
| 65–90 | Uppercase `A`–`Z` |
| 97–122 | Lowercase `a`–`z` |

Those ranges are not arbitrary. Two choices in particular were deliberate and both
still pay off.

**Digits start at 48.** The low four bits of the code for `7` are $0111$, which is
seven. So converting a digit character to its value is a subtraction of $48$, or
equivalently masking off the top bits — no lookup table required.

**Letters are 32 apart.** `A` is $65$ and `a` is $97$. Since $32 = 2^5$, upper and
lower case differ in exactly one bit, so changing case is a single bitwise
operation rather than a table lookup or a comparison chain.

<Aside kind="history" title="Why the top bit was left spare">
ASCII is seven bits, but memory is organised in eight-bit bytes, so one bit per
character was going begging. It was originally used as a **parity bit** for error
detection over noisy telegraph lines: set it so that each byte has an even number
of ones, and any single-bit corruption becomes detectable.

When lines became reliable, that spare bit looked like 128 free character codes,
and everybody helped themselves. Western Europe put accented letters there.
Russia put Cyrillic. Greece put Greek. Israel put Hebrew. All in the same byte
values, all incompatible. A document was now unreadable unless you knew which of
a dozen conventions its author had used, and there was no way to record which
inside the file. Mixing two of them in one document was impossible.

This mess — code pages — is the direct reason Unicode exists.
</Aside>

## Unicode

**Unicode** assigns every character in every writing system its own number,
called a **code point**, written like `U+0041` for `A` or `U+4E2D` for 中. It
currently defines over 150,000 characters and has room for $1{,}114{,}112$.

The crucial distinction, and the one exam questions hinge on:

- A **character set** says which number belongs to which character. Unicode is a
  character set.
- An **encoding** says how that number is turned into bytes. UTF-8 and UTF-16 are
  encodings.

Unicode alone does not tell you how to store `U+4E2D`. You need an encoding for
that, and different encodings produce completely different bytes for the same
character.

## UTF-8

The obvious encoding is to give every character four bytes, since the largest code
point needs 21 bits. It is simple, every character is the same width, and it
wastes three bytes out of four for English text — which, in 1993, was most text.

**UTF-8** is variable length instead, using one to four bytes:

| Code points | Bytes | Covers |
| --- | --- | --- |
| U+0000–U+007F | 1 | ASCII |
| U+0080–U+07FF | 2 | Latin with accents, Greek, Cyrillic, Hebrew, Arabic |
| U+0800–U+FFFF | 3 | Chinese, Japanese, Korean, most remaining scripts |
| U+10000–U+10FFFF | 4 | Historic scripts, emoji, mathematical symbols |

The design has a property that decided the argument: **the one-byte range is
exactly ASCII, byte for byte.** Every ASCII file ever written is already a valid
UTF-8 file. Every program that handled ASCII kept working. Migration cost nothing,
which is why UTF-8 now accounts for around 98% of the web.

<Aside kind="deeper" title="How a decoder knows where a character ends">
A variable-length encoding has an obvious problem: reading byte by byte, how do
you know whether this byte is a whole character or the first of three?

UTF-8 answers it in the leading bits. A byte beginning `0` is a single-byte
character. A byte beginning `110` starts a two-byte sequence, `1110` a three-byte
one, `11110` a four-byte one. Every **continuation** byte begins `10`, and no
starter byte does.

This is self-synchronising: land in the middle of a file, and you can tell
immediately whether you are mid-character, because continuation bytes are
unmistakable. Skip forward until a byte does not begin `10` and you are at a
character boundary. A fixed-width encoding cannot do this, and neither could most
earlier variable-length schemes — losing one byte would garble everything after
it.
</Aside>

## What it costs

Unicode is not free, and two costs matter.

**Size.** Text in a non-Latin script takes two to four times the space of English.
A byte limit is therefore not a character limit, which is a real source of unfairness
in systems that cap message lengths.

**Indexing.** In ASCII, the tenth character starts at byte ten. In UTF-8 it does
not, because you cannot know where it starts without reading everything before it.
Anything that treats a string as an array of fixed-size cells — counting length,
taking a substring, reversing — must be rewritten to walk the string properly.
This is the origin of a great many bugs where an emoji breaks a text box.

<Aside kind="trap" title="Length is not a well-defined idea">
Ask how long the string "👨‍👩‍👧" is and there are four defensible answers: 18 bytes
in UTF-8, 8 UTF-16 units, 5 code points (three people and two invisible joining
characters), or 1 thing a reader would call a character.

Exam answers should say **bytes** or **characters** explicitly rather than
"length". The distinction is exactly what the question is testing.
</Aside>

<Takeaway>
A character set is an agreement about numbers; an encoding is an agreement about
bytes. ASCII conflated the two and got away with it for thirty years because it
only had 128 characters and they all fitted in one byte.
</Takeaway>
