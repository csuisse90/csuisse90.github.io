A file is a sequence of bytes, and most files say the same things repeatedly. A
page of English uses `e` far more than `q`. A photograph of a wall has thousands of
almost identical pixels. Compression exploits that regularity.

There are two fundamentally different bargains available, and choosing the wrong
one is the mistake that matters.

## Lossless

**Lossless** compression re-describes the data more efficiently. Decompress it and
you get back exactly what went in, bit for bit.

This is not optional for most files. Compress a program with a lossy algorithm and
it will not run. Compress a spreadsheet and the numbers change. Compress a legal
document and a word becomes a different word.

### Run-length encoding

The simplest useful method. Replace runs of identical values with the value and a
count.

`WWWWWWWWWWWWBWWWWWWWWWWWWBBB` → `12W1B12W3B`

Twenty-eight characters become ten. On a scanned fax, a line drawing, or a cartoon
with flat colour, this is enormously effective.

On a photograph it is a disaster. Adjacent pixels differ slightly, so runs have
length one, and the output is `1A1B1C1D…` — **twice** the original size. This is
worth internalising, because it generalises: **every compression method assumes
something about the data, and produces bloat when the assumption is false.**

### Dictionary methods

Build a table of sequences that occur repeatedly and replace each occurrence with
a short reference. "the" appearing 400 times in a document is stored once, plus
400 short pointers.

This is what ZIP, PNG and gzip actually use, and it works on almost anything with
structure — text, code, and the row-by-row similarity in images.

### Huffman coding

ASCII gives every character eight bits, whether it is `e` or `~`. That is
wasteful when the frequencies are so uneven.

**Huffman coding** assigns each symbol a code whose length depends on how often it
occurs: frequent symbols get short codes, rare ones long codes.

The codes must form a **prefix code** — no codeword may be the beginning of
another. Without that rule the decoder could not tell where one symbol ended and
the next began; with it, the moment a codeword is recognised it can only be that
symbol, so no separators are needed.

<Py caption="Huffman coding end to end, on real text. Step through the tree-building loop to see the two rarest symbols merge each time.">{`
import heapq
from collections import Counter

def huffman(text):
    freq = Counter(text)
    if len(freq) == 1:
        return {next(iter(freq)): "0"}
    heap = [[n, i, {ch: ""}] for i, (ch, n) in enumerate(freq.items())]
    heapq.heapify(heap)
    tie = len(heap)
    while len(heap) > 1:
        n1, _, left = heapq.heappop(heap)
        n2, _, right = heapq.heappop(heap)
        merged = {ch: "0" + c for ch, c in left.items()}
        merged.update({ch: "1" + c for ch, c in right.items()})
        heapq.heappush(heap, [n1 + n2, tie, merged])
        tie += 1
    return heap[0][2]

text = "the theory that the theatre is there for everyone"
codes = huffman(text)

for ch, code in sorted(codes.items(), key=lambda kv: (len(kv[1]), kv[0])):
    shown = "space" if ch == " " else ch
    print(f"  {shown:>5}  seen {text.count(ch):>2} times  code {code}")

fixed = len(text) * 8
packed = sum(len(codes[ch]) for ch in text)
print()
print(f"ASCII:   {fixed} bits")
print(f"Huffman: {packed} bits")
print(f"ratio:   {fixed / packed:.2f} to 1")

# No codeword is a prefix of another, so this decodes with no separators.
stream = "".join(codes[ch] for ch in text)
back, buffer = "", ""
lookup = {v: k for k, v in codes.items()}
for bit in stream:
    buffer += bit
    if buffer in lookup:
        back += lookup[buffer]
        buffer = ""
print("decoded correctly:", back == text)

## Lossy

**Lossy** compression throws information away permanently. In exchange, it
achieves reductions that lossless methods cannot approach — JPEG routinely reaches
$10{:}1$ where PNG manages $2{:}1$ on the same photograph.

The trick is discarding what a person will not notice. This makes lossy
compression a statement about **human perception**, not about information:

**JPEG** exploits two weaknesses of the eye. First, we resolve brightness far
better than colour, so colour information is stored at reduced resolution. Second,
we notice broad shapes more than fine texture, so the image is broken into blocks,
converted into frequency components, and the high-frequency ones stored coarsely
or dropped.

**MP3** exploits masking in the ear: a loud tone makes a quieter tone at a nearby
frequency inaudible. That quieter tone need not be stored at all, because nobody
can hear it.

<Aside kind="deeper" title="Generation loss, and why you should keep the original">
Lossless compression is idempotent — compress, decompress, compress again, and you
still have the same file. Lossy compression is not. Each save discards more, and
the losses accumulate.

Open a JPEG, crop it, save it, and the whole image has been re-encoded. Do that
twenty times and the degradation is unmistakable: blocky edges, smeared colour,
haloes around detail. This is **generation loss**, and it is why photographers keep
a lossless master and export lossy copies from it rather than editing the copies.

The same reasoning applies to a screenshot of a screenshot, and to audio re-encoded
between formats.
</Aside>

<Aside kind="why" title="Why nothing can compress everything">
It is tempting to imagine a perfect algorithm that shrinks any file. There cannot
be one, and the proof is a counting argument short enough to give here.

Consider all files of exactly $n$ bits. There are $2^n$ of them. Suppose an
algorithm compresses every one to fewer than $n$ bits. The outputs are all of
length $n-1$ or less, and there are only $2^n - 1$ such strings in total. So two
different inputs must produce the same output — and the decompressor cannot
possibly recover both.

Therefore **every lossless compressor makes some files larger.** Real compressors
are useful because the files people actually have are wildly non-random; they win
on those and lose on the noise nobody stores.
</Aside>

<Takeaway>
Lossless asks "can I say this more briefly?". Lossy asks "does anyone need this
part?". The first is a question about the data; the second is a question about the
person looking at it.
</Takeaway>
