Once machines are connected, two separate questions arise. **Topology** asks how
the wires are arranged. **Architecture** asks who is in charge of the conversation.
They are independent: a client–server system can run over any topology.

## Topologies

<Figure caption="The same six devices, arranged four ways. Count the links, and ask what happens if you delete one.">
  <Topology />
</Figure>

**Star.** Every device connects to a central switch. One link per device, so
cabling is cheap and adding a device disturbs nothing. Traffic between any two
devices takes two hops. This is what essentially every office and home network
actually uses.

Its weakness is stated in its shape. Everything depends on the centre, and if the
switch fails the network does not degrade — it stops.

**Bus.** All devices share one backbone. Minimal cable, and it was common when
cable was the expensive part. Now largely historical, because the shared medium
means devices contend for it, and a break anywhere splits the network in two.

**Ring.** Each device connects to two neighbours. Traffic passes round, which makes
timing predictable — useful in industrial control. A single break severs it, so
serious rings are doubled and run in both directions.

**Mesh.** Devices connect to many others. No single point of failure, because
traffic routes around anything broken. The cost is links: a full mesh of $n$ nodes
needs $\frac{n(n-1)}{2}$ of them, so 8 devices need 28 and 50 devices need 1225.

<Aside kind="deeper" title="Why the internet is a mesh and your office is a star">
The trade-off resolves differently depending on what failure costs.

In an office, a failed switch means an hour of irritation and a replacement from
the cupboard. Paying for a mesh to avoid it would be absurd.

The internet's backbone carries the traffic of entire countries, and a severed
cable must not disconnect anyone. So it is meshed, redundantly, with routing
protocols that discover new paths within seconds of a failure.

Both are the right answer to their own question. Exam answers that call one
topology "better" without saying what is being optimised are answering a question
nobody asked.
</Aside>

## The boxes in between

A **hub** repeats every frame to every port. Simple, and wasteful: every device
sees every other device's traffic, collisions are frequent, and privacy is
non-existent. Obsolete.

A **switch** learns. When a frame arrives it records the sender's MAC address
against the port it came in on, building a table. Thereafter, frames for that
address go out of that port alone. Traffic between two pairs of devices can then
happen simultaneously without interfering.

A **router** works one layer up. It forwards packets between *different* networks,
choosing the next hop by looking up the destination IP address in a routing table.
Your home router is really several devices in one box: a router, a switch, a
wireless access point and a firewall.

## Architectures

<Figure caption="In client–server, capacity is what the server has. In peer-to-peer, capacity is the sum of everyone present.">
  <ClientServerVsP2p />
</Figure>

**Client–server** puts data and services on dedicated machines. Clients ask; the
server answers. Because everything is in one place, backup, access control and
updates are all straightforward — you change the server, and every client sees the
change.

The cost is that the server is both a bottleneck and a single point of failure, and
somebody must pay for it.

**Peer-to-peer** has no centre. Every machine is both client and server, offering
what it has and taking what it needs.

The interesting property is how it scales. Under client–server, each additional
user consumes a share of a fixed capacity, so performance degrades as popularity
grows. Under peer-to-peer, each additional user *brings* capacity — a downloader
is also an uploader — so a file becomes easier to obtain the more people want it.

What is lost is control. There is no authority to enforce a security policy, no
guarantee any particular peer is present, and no single place to look when
something is wrong.

## Cloud

**Cloud computing** means using someone else's computers over a network, and paying
for what you use rather than what you own.

The genuine advantages are elasticity and transferred responsibility: capacity can
grow for a busy week and shrink afterwards, and the provider handles hardware
failure, power, cooling and physical security.

The genuine costs are dependence and jurisdiction. The service is unreachable
whenever the internet connection is, which turns a local outage into a total one.
The data sits on hardware belonging to somebody else, possibly in another country
with different laws about who may read it. And rented capacity, over years, is
often dearer than bought capacity.

<Aside kind="trap" title="“The cloud is just someone else's computer” is true but not an argument">
The phrase is accurate and frequently deployed as though it settled the question.
It does not.

What matters is not who owns the hardware but who carries the consequences of it
failing, who has the expertise to run it, and whether demand is steady or spiky. A
school with one part-time technician and a seasonal load is a genuinely different
case from a bank with a data centre and a compliance department.

Marks in a "discuss" question come from weighing those factors for the scenario
given, not from a general verdict on cloud computing.
</Aside>

<Py caption="What each topology costs in links, and what a single failure takes down. The numbers are the whole argument.">{`
def links_needed(topology, n):
    if topology == "star":
        return n                    # one per device, to the switch
    if topology == "bus":
        return 1                    # one shared backbone
    if topology == "ring":
        return n                    # each device joins two neighbours
    if topology == "mesh":
        return n * (n - 1) // 2     # every pair joined
    raise ValueError(topology)

print(f"{'devices':>8}" + "".join(f"{t:>9}" for t in ("star", "bus", "ring", "mesh")))
for n in (4, 8, 16, 32, 64):
    row = "".join(f"{links_needed(t, n):>9,}" for t in ("star", "bus", "ring", "mesh"))
    print(f"{n:>8}{row}")

print()
print("what one failure costs")
for topology, effect in (
    ("star", "the switch fails -> every device is cut off"),
    ("bus", "the backbone breaks -> the network splits in two"),
    ("ring", "one link breaks -> the loop is severed unless doubled"),
    ("mesh", "one link breaks -> traffic routes around it"),
):
    print(f"   {topology:<5} {effect}")

print()
n = 64
print(f"a full mesh of {n} devices needs {links_needed('mesh', n):,} links "
      f"against {links_needed('star', n)} for a star")
print("which is why the resilience is bought only where downtime is expensive")

<Takeaway>
Topology decides what a single failure costs. Architecture decides who holds the
data and therefore who holds the power to control, back up and lose it.
</Takeaway>
