Two ideas make a program bigger than a page manageable: naming a piece of work so
it can be reused, and holding more than one value in a single name.

## Functions

```python
def average(numbers):
    if not numbers:
        return 0
    return sum(numbers) / len(numbers)
```

Three benefits, and questions usually want all three.

**Reuse.** Written once, called anywhere. A fault is fixed in one place.

**Testing.** A function with inputs and a return value can be checked on its own,
without running the whole program.

**Naming.** `average(marks)` says what is happening. Four lines of arithmetic in
the middle of other code does not.

### Parameters, arguments, scope

A **parameter** is the name in the definition; an **argument** is the value passed
at the call. In `average(marks)`, `numbers` is the parameter and `marks` is the
argument.

A variable created inside a function is **local**: it exists while the function
runs and is gone afterwards. That is a feature. It means a function cannot
accidentally clobber a variable somewhere else, and it means you can read the
function without reading the rest of the program.

<Aside kind="trap" title="Why globals make bugs so much harder to find">
A global can be changed by any part of the program. So when it holds the wrong
value, the suspect list is the whole codebase.

A local can only be changed by the ten lines around it. When it holds the wrong
value, you already know where to look.

That is the whole argument, and it is enough. A function whose behaviour depends
only on its parameters can also be tested in isolation, reasoned about in
isolation, and moved elsewhere without dragging state along behind it.

The exam-friendly version: **globals turn a local problem into a global search.**
</Aside>

### Side effects

A **side effect** is anything a function does other than return a value: printing,
writing a file, changing a global, modifying the list it was given.

A function that computes *and* prints cannot be used anywhere the output is
unwanted — inside another calculation, in a test, in a version that writes to a
file. Returning the value and letting the caller decide what to do with it keeps
both options open.

## Collections

| | Ordered | Changeable | Duplicates | Accessed by |
| --- | --- | --- | --- | --- |
| List | Yes | Yes | Yes | Position |
| Tuple | Yes | **No** | Yes | Position |
| Dictionary | Insertion order | Yes | Keys unique | **Key** |
| Set | No | Yes | **No** | Membership |

**List** — the default. Ordered, changeable, indexed from zero.

**Tuple** — a list that cannot be changed. Use one when the values belong together
as a single fixed thing: a coordinate, a date, a database row.

**Dictionary** — key to value. Use when data has a natural identifier: a student
ID, a word, a postcode.

**Set** — no order, no duplicates, very fast at "is this in here?".

<Aside kind="why" title="Why a dictionary lookup does not slow down as it grows">
Finding an item in a list of $n$ means comparing against each in turn: on average
$n/2$ comparisons, and in the worst case $n$. Ten times the data, ten times the
work.

A dictionary computes the key's storage position directly, with a **hash
function** — an arithmetic operation on the key that produces a slot number. It
goes straight there. The number of items in the dictionary does not enter into it.

So a lookup in a dictionary of ten items and one of ten million take about the
same time. That is not an optimisation, it is a different order of behaviour, and
it is why replacing a repeated list search with a dictionary can turn minutes into
milliseconds.

The costs are real but usually small: keys must be hashable and therefore
unchangeable, order is not guaranteed by position, and a dictionary occupies more
memory than a list of the same values.
</Aside>

import time

def average(numbers):
    if not numbers:
        return 0
    return sum(numbers) / len(numbers)

marks = [72, 55, 91, 64, 88]

# Scope: the local does not escape, and the global is untouched.
counter = 0

def broken_increment():
    counter = 1          # makes a new local, does nothing useful
    return counter

def honest_increment(value):
    return value + 1     # takes what it needs, returns what it produced

broken_increment()
print()
print("after broken_increment, the global counter is still", counter)
counter = honest_increment(counter)
print("after honest_increment, it is", counter)

# The four collections.
print()
scores = [72, 55, 91, 55]
point = (3, 4)
by_name = {"Ada": 91, "Alan": 55, "Grace": 78}
seen = {72, 55, 91, 55}

print("list      ", scores, "  keeps order and duplicates")
print("tuple     ", point, "  cannot be changed")
print("dictionary", by_name, "  looked up by key")
print("set       ", sorted(seen), "  duplicates gone")

    point[0] = 9

    print("changing a tuple ->", e)

# Searching a list against looking up in a dictionary.
size = 200_000
big_list = [(f"S{i:06d}", i) for i in range(size)]
big_dict = dict(big_list)
wanted = f"S{size - 1:06d}"

start = time.perf_counter()
for identifier, value in big_list:
    if identifier == wanted:
        break
list_time = time.perf_counter() - start

start = time.perf_counter()
value = big_dict[wanted]
dict_time = time.perf_counter() - start

print()
print(f"searching {size:,} records for the last one")
print(f"   list:       {list_time * 1000:8.3f} ms")
print(f"   dictionary: {dict_time * 1000:8.3f} ms")
print(f"   the dictionary is about {list_time / max(dict_time, 1e-9):,.0f} times faster here")

<Takeaway>
A function should take what it needs, return what it produced, and do nothing
else. A collection should be chosen by how you will reach into it: by position,
by key, or by asking whether something is there.
</Takeaway>
