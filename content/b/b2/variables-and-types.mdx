A variable is a named location in memory. The name is for you; the machine only
ever sees an address.

That framing matters, because it explains behaviour that is otherwise mysterious.
Assignment does not create a copy of a name — it puts a value at a location. Two
names can refer to the same location, and then changing one appears to change the
other.

## Types

A **type** is a promise about what a name holds. It settles three things:

- **How the bits are read.** The same 32 bits are $1{,}078{,}530{,}011$ as an
  integer and $3.14159$ as a float. Nothing in the bits says which.
- **How much space is used.**
- **Which operations are allowed.** Adding two numbers makes sense; adding a
  number to a date does not.

| Type | Holds | Note |
| --- | --- | --- |
| Integer | Whole numbers | Exact, fixed range |
| Real / float | Numbers with a fractional part | **Approximate** |
| Boolean | True or false | One bit of information |
| Character | A single character | A number in a character set |
| String | A sequence of characters | Not a primitive in most languages |

## Static and dynamic typing

**Static typing** fixes a variable's type in advance and checks it before the
program runs. `int count = 5;` and `count = "five"` is rejected by the compiler,
before anybody could suffer from it.

**Dynamic typing** lets a name hold anything and checks as it goes. Python allows
`count = 5` then `count = "five"` without complaint — until something tries to add
to it, at which point it fails, possibly in front of a user.

Neither is better. Static catches a class of error early and makes the code more
verbose; dynamic is quicker to write and defers the error to run time.

<Aside kind="why" title="Why dynamic typing gets slower as well as riskier">
A statically typed compiler knows `a + b` is two integers, so it emits a single
add instruction.

A dynamically typed runtime cannot know. Every `a + b` must first ask what `a` is,
then what `b` is, then decide whether this is integer addition, float addition,
string concatenation, list joining, or an error — and only then do the work. That
check happens on **every execution of that line**, including all million
iterations of a loop.

This is a large part of why Python is slower than C, and why NumPy exists: it
moves the loop into compiled code where the type is known once rather than
re-examined every time.
</Aside>

## Operators worth being careful with

**Division.** Most languages have two. In Python, `/` always gives a real and `//`
gives the integer quotient. `7 / 2` is `3.5`; `7 // 2` is `3`. Get them the wrong
way round and an index calculation silently produces a fraction.

**Modulus.** `%` gives the remainder, and it does more work than its size
suggests. `n % 2 == 0` tests evenness. `n % 7` maps any number onto a day of the
week. `(i + 1) % length` wraps an index round to the start.

**`=` against `==`.** `=` assigns, `==` compares. In Python, `if x = 5` is a syntax
error, which is a kindness. In C it is legal, assigns 5 to `x`, and evaluates as
true — a bug that has caused real damage.

**`+` on strings.** Concatenation, not addition. `"7" + "2"` is `"72"`.

<Aside kind="deeper" title="Why 0.1 + 0.2 is not 0.3">
It is not a bug, and it is not Python's fault. It happens in every language that
uses standard floating point, which is nearly all of them.

Reals are stored in binary, as a fraction times a power of two. A fraction has an
exact binary representation only when its denominator is a power of two. One tenth
is $1/10$, and ten is not a power of two, so $0.1$ in binary recurs forever —
exactly as $1/3$ recurs forever in decimal.

The stored value is the nearest representable number, which is slightly wrong.
Add two slightly wrong numbers and the error can survive into the result:
$0.1 + 0.2$ gives $0.30000000000000004$.

Two consequences worth carrying:

- Never compare reals with `==`. Compare the absolute difference against a small
  tolerance.
- Never store money as a real. Store it as an integer number of pence, or use a
  decimal type. Accumulated rounding on financial data is a real category of bug,
  and it has cost real money.
</Aside>

## Casting

**Casting** converts between types. `int("42")` gives the number; `str(42)` gives
the text.

The discipline that avoids most type bugs is to **convert at the boundary**.
Everything arriving from a text box, a file or a network is text. Convert it once,
on the way in, validating as you go — and then the rest of the program can rely on
having a number.

<Takeaway>
A type is a promise about a value. Static typing checks the promise before the
program runs; dynamic typing checks it as each line executes. Either way, the bugs
come from values whose actual type is not the one the code assumed.
</Takeaway>
