Selection and iteration are two of the three control structures, and between them
they account for most of the logic errors anyone writes. Neither is complicated.
The trouble is in the details.

## Selection

```python
if mark >= 70:
    grade = "7"
elif mark >= 60:
    grade = "6"
else:
    grade = "5"
```

The chain matters. `elif` means *otherwise, if* — evaluation stops at the first
condition that is true, so exactly one branch runs.

Write the same thing with separate `if`s and it breaks:

```python
if mark >= 70:
    grade = "7"
if mark >= 60:     # not elif
    grade = "6"
```

A mark of 85 sets `grade` to `"7"`, then the second condition is also true, so it
is overwritten with `"6"`. Every high mark comes out as a 6.

<Aside kind="trap" title="Order matters in a chain, and the wrong order fails silently">
```python
if mark >= 50: grade = "4"
elif mark >= 70: grade = "7"
```

Nothing here is a syntax error and no warning is produced. But a mark of 85 is
caught by the first condition, so nobody ever gets a 7.

The rule: in a chain of overlapping thresholds, test the **most restrictive**
condition first. When descending through numeric boundaries, that means starting
with the highest.

The test that catches it in seconds is to try one value from each band, including
values exactly on each boundary.
</Aside>

## Boolean operators

Conditions combine with `and`, `or` and `not`. The same three operators as the
logic gates — this is not a coincidence, it is the same algebra.

Two behaviours are worth knowing.

**Short-circuit evaluation.** `A and B` stops if `A` is false, because the answer
is already known. `A or B` stops if `A` is true. This is not only an optimisation:
it lets a guard protect the test that follows it.

```python
if len(items) > 0 and items[0] == target:
```

If the list is empty, the second part is never evaluated, so it never indexes past
the end. Swap the order and it crashes.

**De Morgan's laws apply here too.** `not (a and b)` is `(not a) or (not b)`.
Rewriting a tangled negation this way often makes it readable.

## Iteration

**Count-controlled** — a `for` loop, when you know how many times.

```python
for i in range(5):        # 0, 1, 2, 3, 4
for item in shopping:     # every element in turn
```

**Condition-controlled** — a `while` loop, when you do not.

```python
while not valid:
    mark = int(input("Mark: "))
    valid = 0 <= mark <= 100
```

The choice is decided by one question: **do you know the number of repetitions
before you start?** If yes, `for`. If no, `while`.

## Infinite loops

A `while` loop that never becomes false runs forever.

```python
count = 0
while count < 10:
    print(count)      # count is never changed
```

The rule is that **every path through the body must move the state towards the
condition becoming false**. Notice "every path" — a `continue` that skips the
increment reintroduces the bug for one branch only, which is far harder to spot.

## Nesting and cost

A loop inside a loop runs the body the **product** of the counts. Two loops of
1000 is a million iterations. Two loops of 10,000 is a hundred million.

This is where a program stops being slow and starts being unusable, and it is
usually visible in the shape of the code before it is ever measured: count the
levels of indentation.

<Aside kind="deeper" title="A guard clause is usually clearer than nesting">
Deeply nested conditions are hard to follow because the reader must hold every
enclosing condition in mind at once.

```python
if user is not None:
    if user.active:
        if user.has_permission:
            do_the_thing()
```

Inverting each test and returning early flattens it:

```python
if user is None: return
if not user.active: return
if not user.has_permission: return
do_the_thing()
```

Same behaviour, one level of indentation, and each precondition is stated and
disposed of on its own line. The reader reaches `do_the_thing()` knowing exactly
what must be true, without holding three open brackets in their head.
</Aside>

<Takeaway>
Use `elif` when exactly one branch should run, and order overlapping conditions
most-restrictive first. Use `for` when the count is known and `while` when it is
not — and make sure every path through a `while` body moves towards stopping.
</Takeaway>
