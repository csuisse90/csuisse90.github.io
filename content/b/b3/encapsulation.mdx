Encapsulation is often taught as "make your variables private", which is true and
tells you nothing about why.

The reason is this: **every piece of state that can be changed from outside the
class is a piece of state whose correctness you cannot guarantee.**

## The bank account

A balance that anything may assign to is a balance that can become $-900$. Not
because anybody intends it — because somewhere, in a program of twenty thousand
lines, a subtraction runs in the wrong order.

Make it private and give the class two methods, and the rule lives in exactly one
place:

```python
class BankAccount:
    def __init__(self, opening):
        self._balance = opening

    def withdraw(self, amount):
        if amount <= 0:
            raise ValueError("amount must be positive")
        if amount > self._balance:
            raise ValueError("insufficient funds")
        self._balance -= amount

    def get_balance(self):
        return self._balance
```

Now there is no path to a negative balance. Not "no path anybody has taken" — no
path at all.

## Invariants

The statement "the balance is never negative" is an **invariant**: something true
of every account, always.

An invariant is established by the constructor and preserved by every method. If
that holds, then anywhere in the program, at any moment, you may rely on it
without checking — and *not having to check* is the whole return on the
investment.

<Aside kind="why" title="Why the argument is really about how much you must hold in your head">
Suppose the balance is public and you find one that is negative. Which code did
it? Any of it. Every assignment in the program is a suspect, and you cannot rule
one out without reading it.

Now suppose it is private. The only code that can have done it is inside the
class — perhaps forty lines. You can read all forty and be *certain*.

That is the same argument as the one against global variables, applied one level
up, and it is the deep reason both rules exist. Encapsulation does not make a
program correct. It makes the region you must search when it is not correct small
enough to search.
</Aside>

## Getters, setters, and a common piece of cargo cult

The advice "make attributes private and add a getter and setter for each" is
extremely widespread and mostly wrong.

```python
def set_balance(self, value):
    self._balance = value
```

Anything may still set the balance to anything. The attribute is private in
syntax and public in effect; all that has been added is typing.

A useful accessor is one that either

- **enforces a rule** the class owns, like `withdraw`, or
- **exposes a value without exposing the ability to change it**, like
  `get_balance`, or
- **presents something derived**, like `get_age()` computed from a date of birth.

The design question is not "which fields need accessors?" but "what should this
object be able to do?". Answer that, and the private data follows.

# Version 1: nothing stops anybody.
class LooseAccount:
    def __init__(self, opening):

# Version 2: the rule lives inside the class, so there is no way round it.
class Account:
    def __init__(self, opening):
        if opening < 0:
            raise ValueError("cannot open with a negative balance")
        self._balance = opening          # private by convention

    def deposit(self, amount):
        if amount <= 0:
            raise ValueError("deposit must be positive")
        self._balance += amount

    def withdraw(self, amount):
        if amount <= 0:
            raise ValueError("withdrawal must be positive")
        if amount > self._balance:
            raise ValueError("insufficient funds")
        self._balance -= amount

    def get_balance(self):
        return self._balance

b = Account(250)
b.deposit(50)
print()
print("after depositing 50:", b.get_balance())

for attempt in (400, -10):
    try:
        b.withdraw(attempt)
    except ValueError as e:
        print(f"withdraw({attempt}) refused:", e)

print("balance is still     ", b.get_balance(), " <- the invariant held")

# Changing how it is stored breaks nothing outside the class.
class PennyAccount:
    """Stores pence as an integer, because floats lose money."""
    def __init__(self, opening):
        self._pence = round(opening * 100)

    def deposit(self, amount):
        self._pence += round(amount * 100)

    def get_balance(self):
        return self._pence / 100

for account in (Account(10), PennyAccount(10)):
    account.deposit(0.1)
    account.deposit(0.2)
    print()
    print(type(account).__name__, "reports", account.get_balance())

## Python's version of private

Python has no enforced privacy. It has two conventions:

- A single leading underscore, `_balance`, means "internal — do not touch". Tools
  respect it; the language does not.
- A double leading underscore, `__balance`, triggers **name mangling**: the
  attribute is stored as `_ClassName__balance`, which prevents accidental
  collisions in subclasses but is still reachable by anyone determined.

<Aside kind="deeper" title="Is a convention good enough?">
Java will refuse to compile code that touches a private field. Python will let
you, and merely make it obvious that you are.

In practice the difference matters less than it sounds, because encapsulation's
real job is telling the *reader* which parts of a class are load-bearing. A
leading underscore does that. The compiler check adds enforcement against
deliberate misuse, which is rarely the failure mode — accidents are.

Where the difference does bite is in libraries used by strangers. If anyone can
reach your internals, then in time somebody will, and you can no longer change
them without breaking their code. That is why Python libraries document a public
API carefully and why "we never promised that would keep working" is such a
common argument.
</Aside>

<Takeaway>
Private is not about secrecy. It is about shrinking the amount of code that could
possibly have broken something, and keeping the freedom to change anything nobody
was ever allowed to depend on.
</Takeaway>
