Everything up to now has kept data in one place and the code that works on it in
another. A list of marks over here; a function that averages marks over there.
Nothing links them, and nothing stops you passing the wrong list to the wrong
function.

**Object-oriented programming** puts them together. An object is data plus the
operations allowed on that data, in one thing, with one name.

## Class and object

A **class** is a description. An **object** is a thing.

The class `Dog` says that every dog has a name and an age, and can bark and have
a birthday. It is a piece of writing. No dog exists yet.

`rex = Dog("Rex", 3)` makes one — an **instance**. It has its own memory holding
its own name and age. Making a second dog makes a second set of values, and the
two do not interfere.

The methods are the part people get wrong. They are **not** copied into each
object. `bark()` is stored once with the class, and every object runs that same
code — which is exactly why the method needs to be told which object it is
working on.

## self, and the confusion it causes

```python
class Dog:
    def __init__(self, name, age):
        self.name = name
        self.age = age

    def birthday(self):
        self.age = self.age + 1
```

`self` is the object the method was called on. When you write `rex.birthday()`,
Python calls `Dog.birthday(rex)` — the object arrives as the first argument.

That explains a mistake nearly everyone makes once:

```python
    def birthday(self):
        age = age + 1      # wrong: makes a local, changes nothing
```

Without `self.`, `age` is an ordinary local variable that appears when the method
starts and vanishes when it ends. The dog gets no older, and nothing reports an
error.

<Aside kind="why" title="Why the object has to be passed in at all">
There is one copy of the method's code and potentially a million objects. When
the processor reaches the instruction that adds one to an age, it has to know
*which* age — that is, which address in memory.

So the object's address is passed to the method, exactly like any other argument.
`self` is simply the name that parameter is given. Languages differ only in
whether they make you write it: Java and C++ pass the same thing invisibly and
call it `this`.

Python's choice to make it explicit is why Python beginners meet the idea early
and Java beginners meet it late — and, usually, more painfully.
</Aside>

## The constructor

`__init__` runs when the object is created. Its job is to leave the object in a
state where every other method can rely on the attributes existing and being
sensible.

That last part matters more than it sounds. If a `Dog` can exist with no name,
every method that uses the name must cope with there not being one. Setting it in
the constructor removes an entire class of check from the rest of the program.

## Instance variables against class variables

An **instance variable** belongs to the object: `self.name`. Each object has its
own.

A **class variable** belongs to the class and is shared by every object of it.
The honest use is data that genuinely is common: a count of how many objects have
been created, a shared configuration value, a constant.

<Aside kind="trap" title="The shared mutable class variable">
```python
class Basket:
    items = []          # one list, shared by every basket ever made

    def add(self, thing):
        self.items.append(thing)
```

Two baskets, one list. Adding an apple to yours puts an apple in mine.

It looks right, it type-checks, and it passes any test that only makes one
object. It fails the moment the program has two — which is often in production
rather than in testing.

The fix is to create the list in the constructor, so each object gets its own:

```python
    def __init__(self):
        self.items = []
```

The rule worth carrying: **class variables should be values that are never
mutated.** A shared integer that is only reassigned is usually fine; a shared
list, dictionary or set is almost always a bug in waiting.
</Aside>

## Why bother

Three reasons, and exam questions usually want all three.

**Cohesion.** The data and the operations on it live in one place. To understand
students, you read the `Student` class, not eleven scattered functions.

**Correctness.** Two parallel lists can fall out of step; one list of objects
cannot. Whole categories of bug simply stop being possible.

**Change.** Add a field to a `Student` and you change one class. Add a fourth
parallel list and you change every loop that indexes the other three.

<Takeaway>
A class is a description; an object is one thing made from it, with its own
memory. Methods are shared, which is why they must be told which object they are
working on — and that parameter, `self`, is the difference between changing the
object and changing nothing at all.
</Takeaway>
