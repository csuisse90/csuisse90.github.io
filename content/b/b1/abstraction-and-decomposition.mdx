Two problems make programming hard, and they are not the ones beginners expect.
They are that real problems are too big to hold in your head at once, and that
they contain far more detail than matters.

Decomposition addresses the first. Abstraction addresses the second.

## Decomposition

Break the problem into parts small enough to solve.

"Write a library system" is not a task anybody can start. Split it and it
becomes a list of things that are:

- Members: add, remove, find, check whether they owe a fine.
- Catalogue: add a book, search by title or author, mark as lost.
- Loans: issue, return, renew, list what is overdue.
- Reporting: most borrowed, quietest month, who has what.

Each of those is a task somebody could sit down and do this afternoon.

The benefit is not only that the parts are smaller. It is that each part can be
**tested on its own**, **written by a different person**, and **replaced** without
disturbing the others. A bug is in one box rather than everywhere.

<Aside kind="why" title="How to tell you have decomposed badly">
The test is not how small the parts are. It is how much they need to know about
each other.

If "issue a loan" has to understand how the catalogue stores its books, the split
has bought you nothing — you still have to think about both at once, and changing
one breaks the other. That is **tight coupling**.

A good split leaves each part able to state what it needs in a sentence: "give me
a member id and a book id, I will record the loan or tell you why I cannot." The
parts touch only at their edges.
</Aside>

## Abstraction

A map of the London Underground gets the geography deliberately wrong. Stations
are not where the map says; distances are invented; the river is a shape rather
than a river.

It is one of the most useful documents ever designed, and it is useful *because*
of what it throws away. A passenger needs the order of stations and where lines
cross. Everything else is noise, and removing it is what makes the remainder
readable.

That is **abstraction**: deciding what does not matter for the problem in hand,
and leaving it out.

In programming it appears everywhere:

- A function name says what it does; its body says how. Callers read the name.
- A file looks like a numbered sequence of bytes. It is actually scattered blocks
  on a spinning disc, and you have never had to care.
- A variable called `total` is a location in memory whose address you will never
  learn.

<Aside kind="trap" title="Leaky abstractions, and why they are the ones that bite">
An abstraction promises you need not think about something. It is **leaky** when
that promise fails.

A networked drive looks exactly like a local folder — until the connection drops,
and suddenly a program that only ever "opened a file" is hanging for thirty
seconds. The abstraction hid the network right up to the moment the network was
the only thing that mattered.

Two-dimensional arrays look symmetric, but walking one by rows can be several
times faster than by columns, because underneath it is a single line of memory
and the cache prefers neighbours.

Joel Spolsky's rule is worth remembering: *all non-trivial abstractions leak*. The
point is not to distrust them but to know which detail is hiding underneath, so
that when something behaves strangely you know where to look.
</Aside>

## Pattern recognition

Once a problem is decomposed, parts of it look alike.

"Validate a borrow date" and "validate a return date" are the same problem. "Find
a member by id" and "find a book by id" have the same shape. Noticing this means
writing one thing instead of two — and fixing it in one place instead of two.

<Py caption="The same job written three times, then once. Step through and notice that the third version has the logic in a single place.">{`
students = [
    {"name": "Ada", "mark": 91},
    {"name": "Alan", "mark": 55},
    {"name": "Grace", "mark": 78},
]

# Written out three times. Each is fine; together they are a maintenance problem,
# because a change to the rule has to be made three times and will not be.
top = None
for s in students:
    if top is None or s["mark"] > top["mark"]:
        top = s

bottom = None
for s in students:
    if bottom is None or s["mark"] < bottom["mark"]:
        bottom = s

longest = None
for s in students:
    if longest is None or len(s["name"]) > len(longest["name"]):
        longest = s

print("three separate loops:", top["name"], bottom["name"], longest["name"])

# The pattern is "walk the list keeping the best one so far". Written once, with
# the part that differs passed in.
def best(items, better_than):
    winner = None
    for item in items:
        if winner is None or better_than(item, winner):
            winner = item
    return winner

print("one function:",
      best(students, lambda a, b: a["mark"] > b["mark"])["name"],
      best(students, lambda a, b: a["mark"] < b["mark"])["name"],
      best(students, lambda a, b: len(a["name"]) > len(b["name"]))["name"])
`}</Py>

## Interfaces

The boundary between two parts is an **interface**: what goes in, what comes out,
and nothing about how.

Deciding an interface is deciding what you are promising to keep working. Anything
in the interface is now permanent — callers depend on it. Anything hidden behind it
can be rewritten tomorrow.

This is why "make it private unless it needs to be public" is such a durable rule.
It is not about secrecy. It is about keeping your options open.

<Takeaway>
Decomposition makes a problem small enough to start. Abstraction makes each piece
small enough to finish. Both are decisions about what to ignore, and both are
reversible only while nobody depends on the detail you exposed.
</Takeaway>
