An algorithm is a method written down precisely enough that somebody who does not
understand the problem could still carry it out correctly.

That is a higher bar than it sounds. "Sort the list" is not an algorithm. "Look at
each pair of neighbours in turn, and if the left one is bigger, swap them; repeat
until a full pass makes no swaps" is.

## What makes it an algorithm

**Finite.** It stops. A method that might run forever is not an algorithm, however
correct each step is.

**Unambiguous.** Every step has exactly one meaning. "Pick a suitable value" is not
a step.

**Defined input and output.** It is clear what it needs and what it produces.

**Effective.** Every step can actually be performed. "Determine whether this
program halts" is unambiguous and impossible.

## Sequence, selection, iteration

Every algorithm ever written is built from three structures.

**Sequence** — do this, then that. **Selection** — if this, do that, otherwise the
other. **Iteration** — do this repeatedly, while or until something.

That is the entire vocabulary. It is worth pausing on how small the list is: no
matter how elaborate the program, there is nothing else in it.

## Pseudocode

Pseudocode is structured English: precise about logic, silent about syntax.

```
largest ← first number
FOR each remaining number
    IF number > largest THEN
        largest ← number
    ENDIF
ENDFOR
OUTPUT largest
```

Nobody can run that, which is the point. The design is being checked, not the
spelling of a keyword. It can also be read by someone who does not know your
language, and implemented in any of them.

<Aside kind="trap" title="Where marks go missing in a pseudocode question">
Examiners are not marking syntax; they are marking whether the logic works. The
losses are almost always one of four things.

**The variable is never initialised.** `largest` is compared before it holds
anything.

**The output is inside the loop.** The answer is printed once per iteration rather
than once at the end.

**The loop bound is wrong by one.** Starting at 1 when the data starts at 0, or
using `<` where `≤` was needed.

**The empty case is not considered.** "The first number" does not exist if there
are no numbers.

Reading your own pseudocode back with a list of *two* items, and then with a list
of *none*, catches nearly all of these in under a minute.
</Aside>

| Diamond | A decision, with two labelled exits |

The strength of a flowchart is that a loop is visibly a loop — a line going back
where it came from. The weakness is that anything longer than about twenty steps
becomes a plate of spaghetti, which is why real designs use pseudocode and keep
flowcharts for explaining a single mechanism.

## Trace tables

A **trace table** records how the variables change, one row per step. It is how
you check an algorithm without running it, and it is directly examined.

For `total ← 0; count ← 1; WHILE count ≤ 4 DO total ← total + count; count ← count + 1`:

| Step | count | total | count ≤ 4 |
| --- | --- | --- | --- |
| start | 1 | 0 | true |
| 1 | 2 | 1 | true |
| 2 | 3 | 3 | true |
| 3 | 4 | 6 | true |
| 4 | 5 | 10 | **false** |
| output | | 10 | |

Note the last row. `count` reaches 5 and the loop stops — the variable ends one
past the last value it was used for, which is exactly where off-by-one errors come
from and exactly what a trace table exposes.

<Py step caption="Step through this and switch to the trace-table view. That table is the one an exam question asks you to complete by hand.">{`
def largest(numbers):
    if not numbers:
        return None
    biggest = numbers[0]
    for value in numbers[1:]:
        if value > biggest:
            biggest = value
    return biggest

def total_to(n):
    total = 0
    count = 1
    while count <= n:
        total = total + count
        count = count + 1
    return total

print("largest:", largest([3, 17, 9, 42, 8]))
print("largest of nothing:", largest([]))
print("total to 4:", total_to(4))

# The classic off-by-one, side by side.
data = ["a", "b", "c"]
print()
print("range(len(data)) visits", [i for i in range(len(data))], "— correct")
print("range(1, len(data)) visits", [i for i in range(1, len(data))], "— misses the first")
`}</Py>

<Aside kind="deeper" title="Why “it works on my example” is not evidence">
An algorithm tested on one input has been shown to work on one input.

The inputs that break things are almost never the typical ones. They are the
**edges**: nothing at all, exactly one item, two identical items, the largest
value first, the largest value last, a value that is negative when you assumed
positive.

A short discipline that catches most of it: before writing any loop, ask what it
does when the collection is empty and when it has exactly one element. Both are
answerable in a few seconds, and between them they account for a large share of
the bugs in student code — and a fair share in professional code too.
</Aside>

<Takeaway>
Sequence, selection and iteration are the whole vocabulary. Pseudocode checks the
logic before the syntax can distract from it, and a trace table checks the logic
before the computer can.
</Takeaway>
