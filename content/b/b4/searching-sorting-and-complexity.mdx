Two questions decide whether a program works at scale: how you find something,
and how you put things in order. Both have well-known answers, and the
differences between them are enormous.

## Searching

### Linear search

Look at each element until you find it or run out.

$n$ comparisons in the worst case, $n/2$ on average, and — the thing people
forget to say — **it works on unsorted data**. That is its whole advantage.

### Binary search

If the data is sorted, compare with the middle. The target is either that element
or in one of the halves, and the other half can be discarded entirely.

<Figure caption="Each comparison throws away half of what is left. Four steps are enough for twelve items; twenty are enough for a million.">
  <BinarySearchSteps />
</Figure>

The maximum number of comparisons is $\lceil \log_2 n \rceil$:

| Items | Linear (worst) | Binary (worst) |
| --- | --- | --- |
| 100 | 100 | 7 |
| 1,000 | 1,000 | 10 |
| 1,000,000 | 1,000,000 | 20 |
| 1,000,000,000 | 1,000,000,000 | 30 |

Notice the shape: a thousandfold increase in data adds ten comparisons.

<Aside kind="trap" title="Sorting first is not always worth it">
"Binary search is faster, so sort the data first" is wrong as often as it is
right.

Sorting costs $O(n \log n)$. A single linear search costs $O(n)$. Sorting in
order to make one search is strictly more expensive than just searching.

The sum for $k$ searches is:

- Linear throughout: $k \times n$
- Sort once, then binary: $n \log n + k \log n$

So sorting pays off when $k$ is large — many searches over data that does not
change. It does not pay off for one search, and it does not pay off if the data
changes between searches, because then you are sorting repeatedly.

This is exactly why a database index is built once and then reused, and why
building an index on a table you only query once is a waste.
</Aside>

## Sorting

### Bubble sort

Compare adjacent pairs, swap if out of order, repeat. After each pass the largest
remaining element has reached the end.

Its only virtues are that it is easy to write and easy to trace, which is why it
is taught. With a swap flag it detects an already-sorted list in one pass —
$O(n)$ in the best case — but $O(n^2)$ otherwise.

### Selection sort

Find the smallest element, swap it into position 0. Find the smallest of the
rest, swap into position 1. Continue.

Always $O(n^2)$ comparisons regardless of the input, but at most $n$ swaps, which
matters if a swap is expensive — moving large records rather than integers.

### Insertion sort

Take each element and slide it back into place among those already sorted, like
putting a card into a hand you are holding.

$O(n^2)$ in general, but **$O(n)$ on nearly sorted data**, because each element
moves only a little. That makes it genuinely useful: real production sorts switch
to insertion sort for small chunks.

### Merge sort

Split the list in half, sort each half — recursively, by the same method — then
merge the two sorted halves.

<Figure caption="Splitting costs nothing. The work is the merging, and there are only log n levels of it.">
  <MergeSortTree />
</Figure>

Merging two sorted lists is easy: repeatedly take the smaller of the two front
elements. Each level of merging touches all $n$ items, and there are $\log_2 n$
levels, which is where $O(n \log n)$ comes from.

It needs extra memory for the merged output, which is its one real cost.

| Sort | Best | Average | Worst | Extra memory | Stable |
| --- | --- | --- | --- | --- | --- |
| Bubble | $O(n)$ | $O(n^2)$ | $O(n^2)$ | $O(1)$ | Yes |
| Selection | $O(n^2)$ | $O(n^2)$ | $O(n^2)$ | $O(1)$ | No |
| Insertion | $O(n)$ | $O(n^2)$ | $O(n^2)$ | $O(1)$ | Yes |
| Merge | $O(n\log n)$ | $O(n\log n)$ | $O(n\log n)$ | $O(n)$ | Yes |

## Big-O

Big-O says how the work grows with $n$, and deliberately ignores everything else.

<Figure caption="Constant factors move a curve up and down. They cannot change its shape, and the shape is what decides whether a program finishes.">
  <ComplexityCurves />
</Figure>

Two rules explain why it looks the way it does.

**Constants are dropped.** $3n$ and $n$ are both $O(n)$. A constant depends on
the machine, the language and the compiler, so it cannot distinguish one
algorithm from another.

**Only the fastest-growing term survives.** $n^2 + 500n + 9000$ is $O(n^2)$. At
$n = 10$ the other terms dominate; at $n = 100{,}000$ the $n^2$ term is ten
thousand times larger than everything else put together.

<Aside kind="why" title="Why the shape beats the constant, with numbers">
Suppose an $O(n^2)$ algorithm is written in tuned C and an $O(n \log n)$ one in
Python, so each step of the first is **100 times faster**.

| $n$ | $n^2$ steps ÷ 100 | $n \log_2 n$ steps |
| --- | --- | --- |
| 100 | 100 | 664 |
| 1,000 | 10,000 | 9,966 |
| 10,000 | 1,000,000 | 132,877 |
| 1,000,000 | 10,000,000,000 | 19,931,569 |

The fast implementation wins at $n = 100$, draws at about $n = 1{,}000$, and by a
million is five hundred times slower — *despite each step being a hundred times
faster*.

That is the whole argument for caring about complexity. Hardware and clever
coding buy you a constant factor. Only a better algorithm changes the shape, and
the shape is what decides whether the program finishes at all.
</Aside>

def linear_search(data, target):
    for index, value in enumerate(data):
        if value == target:
            return index, index + 1
    return None, len(data)

def binary_search(data, target):
    low, high, comparisons = 0, len(data) - 1, 0
    while low <= high:
        mid = (low + high) // 2
        comparisons += 1
        if data[mid] == target:
            return mid, comparisons
        if data[mid] < target:
            low = mid + 1
        else:
            high = mid - 1
    return None, comparisons

def bubble_sort(data):
    items, comparisons, swaps = list(data), 0, 0
    for end in range(len(items) - 1, 0, -1):
        swapped = False
        for i in range(end):
            comparisons += 1
            if items[i] > items[i + 1]:
                items[i], items[i + 1] = items[i + 1], items[i]
                swaps += 1
                swapped = True
        if not swapped:
            break                        # already in order
    return items, comparisons, swaps

def selection_sort(data):
    items, comparisons, swaps = list(data), 0, 0
    for start in range(len(items)):
        smallest = start
        for i in range(start + 1, len(items)):
            comparisons += 1
            if items[i] < items[smallest]:
                smallest = i
        if smallest != start:
            items[start], items[smallest] = items[smallest], items[start]
            swaps += 1
    return items, comparisons, swaps

def insertion_sort(data):
    items, comparisons, moves = list(data), 0, 0
    for i in range(1, len(items)):
        held, j = items[i], i - 1
        while j >= 0:
            comparisons += 1
            if items[j] <= held:
                break
            items[j + 1] = items[j]
            moves += 1
            j -= 1
        items[j + 1] = held
    return items, comparisons, moves

def merge_sort(data, counter=None):
    if counter is None:
        counter = [0]
    if len(data) <= 1:
        return data, counter[0]
    middle = len(data) // 2
    left, _ = merge_sort(data[:middle], counter)
    right, _ = merge_sort(data[middle:], counter)
    merged, i, j = [], 0, 0
    while i < len(left) and j < len(right):
        counter[0] += 1
        if left[i] <= right[j]:
            merged.append(left[i]); i += 1
        else:
            merged.append(right[j]); j += 1
    merged.extend(left[i:]); merged.extend(right[j:])
    return merged, counter[0]

<Takeaway>
Sorted data buys you $O(\log n)$ searching, and sorting itself is $O(n \log n)$
if you use a divide-and-conquer method. Constant factors decide which of two
similar algorithms wins; the exponent decides whether the program finishes.
</Takeaway>
