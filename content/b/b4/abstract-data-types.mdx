Everything in this unit rests on one distinction, so it is worth being pedantic
about it.

An **abstract data type** is a promise: these are the values, these are the
operations. A **data structure** is a way of keeping that promise.

"Stack" is an ADT. It promises `push`, `pop` and `isEmpty`, and it promises that
what comes out is what went in most recently. It says nothing about arrays,
nodes, or memory.

The point of naming the abstract type separately is that everything written
against it survives a change of implementation. Start with an array because it is
simple; discover it overflows; swap in linked nodes; and not one line of calling
code changes.

## Static and dynamic

A **static** structure is sized once. An array of 100 integers is 100 integers'
worth of memory, whether you use two or a hundred, and there is no hundred and
first.

A **dynamic** structure allocates as it goes. Each element is a separate
allocation, linked to the others by pointers, and there is no fixed limit beyond
the memory available.

| | Static (array) | Dynamic (linked) |
| --- | --- | --- |
| Size | Fixed at creation | Grows and shrinks |
| Memory per element | Just the data | Data **plus** a pointer |
| Access by index | Immediate | Walk from the start |
| Insert at the front | Shift everything | Change one pointer |
| Memory layout | One consecutive block | Scattered |

Neither wins. They are good at the opposite things, and that is the whole basis
for choosing between them.

<Aside kind="why" title="Why indexing an array is a single calculation">
An array is one consecutive block, and every element is the same size. So the
address of element $i$ is

$$
\text{address} = \text{base} + i \times \text{size}
$$

That is a multiply and an add. It takes the same time for element 0 and element
999,999, which is what "constant time" means.

A linked list cannot do this. Its nodes are wherever the allocator put them, so
the only way to find the tenth is to read the first, follow its pointer to the
second, and so on. Ten steps for the tenth, a million for the millionth.

The compensation is that an array's virtue is also its constraint: because
everything is consecutive, making room in the middle means physically moving
everything after it.
</Aside>

## The cost table worth memorising

For $n$ elements:

| Operation | Array | Linked list |
| --- | --- | --- |
| Read element $i$ | $O(1)$ | $O(n)$ |
| Insert at the front | $O(n)$ | $O(1)$ |
| Insert at the end | $O(1)$ if room | $O(1)$ with a tail pointer |
| Insert in the middle | $O(n)$ | $O(1)$ **once you are there** |
| Delete a known element | $O(n)$ | $O(1)$ |
| Search for a value | $O(n)$ | $O(n)$ |

The row that catches people is the middle insertion. A linked list inserts in
constant time *given a pointer to the position*; finding that position is $O(n)$.
Quoting $O(1)$ without the caveat loses the mark.

<Aside kind="deeper" title="The cache, and why arrays beat the theory">
The table says a linked list wins for insertion. Real machines complicate this.

Memory is not read one byte at a time. The processor fetches a **cache line** —
typically 64 bytes — so reading element 0 of an array drags the next fifteen
integers into fast memory for nothing. Walking an array is therefore close to
free per element after the first.

Linked-list nodes are scattered. Each hop is potentially a fresh cache miss
costing a hundred times what a cached read costs. So an array can beat a linked
list at insertion, despite doing more work, until $n$ becomes large — because
memmove on consecutive memory is one of the fastest things a computer does, and
pointer chasing is one of the slowest.

This does not change the exam answer, which is about orders of growth. It is why
professional code uses arrays far more often than the table suggests.
</Aside>

import time

# --- a linked list, built out of nodes so the pointers are visible -----------
class Node:
    def __init__(self, value):
        self.value = value
        self.next = None

class LinkedList:
    def __init__(self):
        self.head = None
        self.count = 0

    def push_front(self, value):
        node = Node(value)
        node.next = self.head        # one pointer write
        self.head = node             # and one more
        self.count += 1

    def get(self, index):
        node = self.head
        for _ in range(index):       # no shortcut exists
            node = node.next
        return node.value

    def to_list(self):
        out, node = [], self.head
        while node:
            out.append(node.value)
            node = node.next
        return out

small = LinkedList()
for v in (9, 7, 12):
    small.push_front(v)
print("linked list:", small.to_list(), " head is the last one pushed")
print("element 2  :", small.get(2), " reached by walking two links")

# --- the same two operations, timed, on both structures ----------------------
N = 20_000

array = []

    array.insert(0, i)               # shifts everything, every time
array_front = time.perf_counter() - start

## Choosing

The question is never "which structure is best". It is **which operations does
this program do most?**

- Reading by position, rarely changing the size → **array**.
- Constant insertion and deletion, order matters, position does not → **linked
  list**.
- Only ever touching one end → **stack**.
- Adding at one end, removing from the other → **queue**.
- Looking things up by a key → **hash table**.
- Keeping things sorted while still inserting → **tree**.

<Takeaway>
Name the operations first and the storage second. The ADT is what your program
depends on; the data structure is a decision you should be able to reverse
without anybody noticing.
</Takeaway>
