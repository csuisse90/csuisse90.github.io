A recursive function is one that calls itself. The idea is small; what it does to
memory is where the understanding lives.

## The two parts

Every recursive function has exactly two kinds of case, and both are compulsory.

```python
def factorial(n):
    if n <= 1:            # base case: answerable without recursing
        return 1
    return n * factorial(n - 1)   # recursive case: a smaller problem
```

The **base case** stops it. The **recursive case** must move towards the base
case — strictly smaller each time, or it will never arrive.

Omit the base case and nothing catches the fall. The function calls itself until
the stack is exhausted and the program dies.

## What it builds

`factorial(4)` does not compute anything on the way down. It cannot: it needs
`factorial(3)` before it can multiply, and that needs `factorial(2)`, and so on.

So four calls pile up, each waiting. Only when `factorial(1)` returns 1 does any
arithmetic happen, and then the answers unwind back up.

Each waiting call is a **stack frame** holding its own `n`, its own local
variables, and the address to return to. Depth $n$ costs $n$ frames — which is
the whole memory argument against recursion, and the reason a recursion 100,000
deep crashes where a loop would not.

<Aside kind="why" title="Why the stack is small, and what happens when it fills">
The call stack is a fixed block of memory reserved when a thread starts —
typically 1 MB, sometimes 8 MB. It is deliberately modest, because every thread
gets one and a server may run thousands.

A frame for a simple function is perhaps 50–100 bytes, so a megabyte allows
roughly ten to twenty thousand frames. Python's own limit is lower still — about
1,000 by default — and it raises `RecursionError` before the real stack runs out,
because a genuine C-level stack overflow cannot be caught and would take the
whole interpreter down.

That is why a stack overflow is a *crash* rather than an exception in most
languages. There is no memory left in which to run the error handler.
</Aside>

## The Fibonacci trap

The textbook second example of recursion is also a good example of recursion done
badly.

```python
def fib(n):
    if n <= 1:
        return n
    return fib(n - 1) + fib(n - 2)
```

Correct, elegant, and catastrophically slow. Each call makes two more, so the
number of calls roughly doubles with every increase in $n$: about $2^n$ calls for
`fib(n)`.

The reason is that it recomputes. Calculating `fib(30)` computes `fib(28)` twice,
`fib(27)` three times, `fib(5)` hundreds of thousands of times.

**Memoisation** fixes it. Store each answer the first time and look it up
thereafter. The work drops from exponential to linear, from about 2.7 million
calls to 31.

<Aside kind="deeper" title="Why recursion gets blamed for this">
It is worth being precise: the exponential behaviour is not caused by recursion.
It is caused by solving the same subproblem repeatedly. The same algorithm
written with a loop that recomputed in the same way would be just as slow.

What recursion does is make that mistake easy to write and hard to see. The code
looks like the mathematical definition, and the mathematical definition says
nothing about how many times each term is evaluated.

This is the origin of **dynamic programming**: recognise the overlapping
subproblems, then either store the results as you go (memoisation, top-down) or
compute them in order from the bottom (tabulation, bottom-up). Both turn the same
recursive insight into something that finishes.
</Aside>

calls = 0

def fib(n):
    global calls
    calls += 1
    if n <= 1:
        return n
    return fib(n - 1) + fib(n - 2)

print()
print(" n   fib(n)   calls made")
for n in (5, 10, 20, 25):
    calls = 0
    value = fib(n)
    print(f"{n:2}   {value:6}   {calls:,}")

# The same function, remembering what it has already worked out.
memo = {}
memo_calls = 0

def fib_fast(n):
    global memo_calls
    memo_calls += 1
    if n in memo:
        return memo[n]
    memo[n] = n if n <= 1 else fib_fast(n - 1) + fib_fast(n - 2)
    return memo[n]

memo.clear()
memo_calls = 0
value = fib_fast(25)
print()
print(f"with memoisation: fib(25) = {value} in {memo_calls} calls")
print("Same recursion. The only change is not solving the same thing twice.")

import sys
def count_down(n):
    return 0 if n == 0 else 1 + count_down(n - 1)

## Recursion against iteration

| | Recursion | Iteration |
| --- | --- | --- |
| Memory | One frame per level | One frame total |
| Speed | A call per step | No call overhead |
| Depth limit | Yes — the stack | No |
| Clearer for | Trees, nesting, divide and conquer | Plain repetition |

Anything recursive can be written iteratively and the reverse, so the choice is
about clarity and cost, not capability.

Use **iteration** for straightforward repetition. `factorial` as a loop is
shorter, faster and unlimited in depth; the recursive version is a teaching
example rather than a recommendation.

Use **recursion** when the *data* is recursive. A tree's children are trees. A
folder's contents include folders. A nested list contains lists. Writing those
iteratively means building your own stack to remember where to come back to —
which is doing by hand exactly what the call stack was doing for free.

<Takeaway>
Recursion needs a base case, and every call that has not returned costs a frame.
Reach for it when the problem is genuinely self-similar; reach for a loop when it
is merely repetitive — and watch for the same subproblem being solved twice.
</Takeaway>
