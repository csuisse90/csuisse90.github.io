A linked list has one `next`. Give a node two, and it stops being a line and
becomes a **tree**.

## The vocabulary

Trees are drawn upside down: the **root** at the top, **leaves** at the bottom.

- **Root** — the one node with no parent.
- **Parent** and **child** — the node above, and the nodes directly below.
- **Leaf** — a node with no children.
- **Subtree** — any node together with everything below it. This is the important
  one: every subtree is itself a tree, which is why nearly every tree algorithm
  is recursive.
- **Height** — the number of levels, or the longest root-to-leaf path.
- **Binary tree** — every node has at most two children.

## The binary search tree rule

> For every node, everything in its left subtree is smaller and everything in its
> right subtree is larger.

Note **every node**, not just the root. That is what makes the structure work.

### Searching

```
current ← root
WHILE current ≠ null
    IF target = current.value THEN found
    ELSE IF target < current.value THEN current ← current.left
    ELSE current ← current.right
END WHILE
```

Each comparison eliminates an entire subtree. In a tree of height $h$, a search
takes at most $h$ comparisons — and a balanced tree of $n$ nodes has
$h \approx \log_2 n$. A million values, twenty comparisons.

### Inserting

Search for the value. When you fall off the bottom, that empty place is where it
belongs. A new value is therefore always inserted as a leaf.

<Aside kind="trap" title="Sorted input destroys a binary search tree">
Insert 10, 20, 30, 40, 50 into an empty tree.

10 is the root. 20 is larger, so right. 30 is larger than both, so right again.
Every value goes right.

The result is a chain — a linked list wearing a tree's clothes. Its height is $n$
instead of $\log_2 n$, and searching it costs $n$ comparisons.

This is not a rare accident. Data very often arrives sorted: records exported by
ID, timestamps, alphabetical names. It is exactly the case a naive binary search
tree handles worst, and it is why **self-balancing** trees exist — AVL and
red–black trees rotate nodes on insertion to keep the height near $\log_2 n$
regardless of the input order.

The exam-level version: a binary search tree is $O(\log n)$ **when balanced** and
$O(n)$ in the worst case. Quoting the first without the condition loses a mark.
</Aside>

## The three traversals

Every traversal does the same three things — visit the node, go left, go right —
in a different order. The name tells you where the *node* comes.

| Traversal | Order | Produces |
| --- | --- | --- |
| **Pre**-order | **Node**, left, right | A sequence that rebuilds the tree |
| **In**-order | Left, **node**, right | The values in ascending order |
| **Post**-order | Left, right, **node** | Children before parents |

Each has a job.

**In-order** on a binary search tree gives sorted output. That is not a
coincidence — it is the tree rule read out loud.

**Pre-order** writes the root first, so replaying it into an empty tree rebuilds
the same shape. It is how a tree is copied or saved to a file.

**Post-order** finishes both children before the parent. That is what you need
when the parent's work depends on its children's: deleting a tree (you cannot
free a node while its children still hang off it), or evaluating an expression
tree (you cannot apply an operator before both operands are known).

<Aside kind="why" title="Expression trees, and why post-order is reverse Polish">
The expression $(3 + 4) \times 5$ as a tree has $\times$ at the root, the $+$
subtree on the left and $5$ on the right.

- **In-order** gives `3 + 4 × 5` — the way we write it, and ambiguous without the
  brackets the tree already encoded.
- **Post-order** gives `3 4 + 5 ×` — reverse Polish notation, which needs no
  brackets at all.
- **Pre-order** gives `× + 3 4 5` — Polish notation, the same idea the other way
  round.

Reverse Polish evaluates with a stack and no precedence rules: push numbers, and
on an operator pop two, apply, push the result. That is why calculators and
virtual machines use it, and why post-order traversal is the natural way to
evaluate an expression.

Two structures from this unit fit together here: the tree records the structure
of the expression, and the stack evaluates it.
</Aside>

class TreeNode:
    def __init__(self, value):
        self.value = value
        self.left = None
        self.right = None

class Bst:
    def __init__(self):
        self.root = None

    def insert(self, value):
        if self.root is None:
            self.root = TreeNode(value)
            return
        node = self.root
        while True:
            if value < node.value:
                if node.left is None:
                    node.left = TreeNode(value)
                    return
                node = node.left
            elif value > node.value:
                if node.right is None:
                    node.right = TreeNode(value)
                    return
                node = node.right
            else:
                return                      # already present

    def find(self, value):
        node, steps = self.root, 0
        while node is not None:
            steps += 1
            if value == node.value:
                return steps
            node = node.left if value < node.value else node.right
        return None

    def height(self, node="start"):
        if node == "start":
            node = self.root
        if node is None:
            return 0
        return 1 + max(self.height(node.left), self.height(node.right))

    def in_order(self, node="start", out=None):
        if node == "start":
            node, out = self.root, []
        if node is not None:
            self.in_order(node.left, out)   # everything smaller
            out.append(node.value)          # then this
            self.in_order(node.right, out)  # then everything larger
        return out

    def pre_order(self, node="start", out=None):
        if node == "start":
            node, out = self.root, []
        if node is not None:
            out.append(node.value)
            self.pre_order(node.left, out)
            self.pre_order(node.right, out)
        return out

    def post_order(self, node="start", out=None):
        if node == "start":
            node, out = self.root, []
        if node is not None:
            self.post_order(node.left, out)
            self.post_order(node.right, out)
            out.append(node.value)
        return out

tree = Bst()
for v in (50, 30, 70, 20, 40, 60, 85):
    tree.insert(v)

print("in-order   ", tree.in_order(), " <- sorted, for free")
print("pre-order  ", tree.pre_order(), " <- rebuilds this exact shape")
print("post-order ", tree.post_order(), " <- children before parents")
print()
print("height", tree.height(), "for", len(tree.in_order()), "nodes")
print("find 40 ->", tree.find(40), "comparisons")
print("find 85 ->", tree.find(85), "comparisons")
print("find 41 ->", tree.find(41), "(not present)")

## Balance

Height is everything. A tree of $n$ nodes can have height as small as
$\log_2 n$ or as large as $n$, and every operation costs the height.

A **balanced** tree keeps the two subtrees of every node within one level of each
other. Self-balancing trees do it automatically by rotating nodes during
insertion. You are not required to implement one, but you are expected to know
why they exist: because the unbalanced case is not a rare misfortune, it is what
sorted input produces.

<Takeaway>
The binary search tree rule holds at every node, and that is what buys ordered
traversal and halving searches. Both benefits are only as good as the tree's
balance — a tree built from sorted data is a linked list with extra pointers.
</Takeaway>
